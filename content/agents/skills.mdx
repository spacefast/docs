The Spacefast plugins and `sf skills install` install the base `spacefast` skill for publishing, inspection, and management. The format and tool choices depend on the client. Adding only an MCP connection doesn't install the skill.

The plugins also include task skills for building a Space, editing a Space, sharing, custom domains, fixing a deployment, and saving and using a team's Design System.

## The base `spacefast` skill

Every install method ships a skill named `spacefast`: a `SKILL.md` and a `references.md`, rendered from one template into per-client variants.

| Method | What lands |
|---|---|
| Claude Code plugin | `skills/spacefast/` and the task skills |
| Codex plugin | The same skills in the Codex variant |
| Cursor plugin | The same skills, plus a `rules/spacefast.mdc` rule |
| `sf skills install` | `spacefast/SKILL.md` and `references.md` in the client's skills directory |

The plugins carry the MCP variant, which routes work to the typed tools. The copy bundled with the CLI carries the curl and HTTP API variant instead, for agents that have no MCP connection at all.

## Design System task skills

The Claude Code, Codex, and Cursor plugins in [release 0.5.8](https://github.com/spacefast/plugins/releases/tag/plugins-v0.5.8) include four skills for the [Design System](/design-system). If your installed plugin lacks these skills, update it before using the Design System prompts.

| Skill | Use it for |
|---|---|
| `import-design-system` | Save supplied standards, source files, and supporting guidance to the team |
| `apply-design-system` | Use saved standards in a new build or requested source edit |
| `verify-design-system` | Check a source build or preview against current standards; fix only when you ask for corrections |
| `update-design` | Bring a named existing Space or linked project onto current standards |

Importing standards does not change a project. Applying them to one project does not roll them out to the team's other Spaces.

## What the base skill instructs

The skill's job is routing and conduct. The MCP variant follows these tool choices.

| Job | Tool |
|---|---|
| Publish local files or a new inline artifact | `publish` |
| View deployments, domains, analytics, source, or build logs | The matching Space App tool |
| Check an active publish | `operation_status` |
| Documentation, account context, other API reads, and mutations | The matching API operation tool |
| Continue an approval | `resume_execution` |

The rest sets behavior the tools alone do not enforce.

- Call the matching operation tool directly. Read its input schema before calling it.
- Reuse the `.spacefast/` link in the current directory. Do not list Spaces before an ordinary publish, and set `createNew` only when you asked for a separate Space.
- Publish once, then poll `operation_status` until it settles, then read the deployment, then report.
- Report the live URL and the immutable version URL, plus the access URL when the receipt includes one. Current clients create team-owned Spaces without automatic access URLs: the owning team signs in at the live URL, and `sf share link create` makes a link for people outside the team. For an anonymous publish, relay the receipt's claim link and message so the owner can keep the Space. Treat the link as a credential.
- Never print API keys, Space keys, upload tokens, or `.spacefast/state.json`.
- Open the URL before claiming success, since a bare live URL is private until access is granted.

`references.md` holds the deeper material, hosted versus On-Device differences, the update and claim flow, approvals and `resume_execution`, and signed uploads. The skill tells the agent to load it only when the question actually needs it.

## Kept in sync with the tools

A CI check re-renders every skill variant and compares the tool names it mentions against the live tool list, in both directions. A tool added without a skill update fails the build, and so does a skill that names a tool which no longer exists. The tool catalog comes from the API operations; read the current [MCP reference](/agents/mcp-server#the-tools).

## Install the base skill on its own

If you want the skill without touching MCP config, the CLI installs the copy bundled with it.

```bash
sf skills install
```

| Flag | What it does |
|---|---|
| `--agent <id>` | Install for one agent. Repeat for more. `auto` uses detected agents plus `.agents/skills`. `all` installs everywhere |
| `--project` | Install into this project instead of the agent's global skills directory |
| `--list` | List the bundled skill files without installing |
| `--force` | Overwrite locally modified or unverified Spacefast skill files |

Two sibling commands round it out.

```bash
sf skills status
sf skills remove
```

`sf skills remove` confirms before it deletes, and with `--force` it removes only the files the install manifest owns. Your own files in the same directory survive.

There is also a standalone installer that does not need the `sf` CLI.

```bash
npx -y skills add spacefast/plugins --skill spacefast -g -y
```

## Install and update behavior

Installs are fail-closed. If the skill directory holds a file the manifest does not recognize, the CLI marks the state unverifiable and refuses to install or remove without `--force`. Only `.DS_Store`, `.localized`, `Thumbs.db`, and `desktop.ini` are exempt.

The bundled skill refreshes itself. Almost every `sf` command upgrades an installed skill in the background, but only when the installation still matches its manifest. A copy you edited is left alone.
