Spacefast Share (formerly Spacefast Access) controls who can open a Space. Access comes from grants, and any matching grant lets a visitor in. Removing one public grant doesn't remove other public grants, links, people, or team access.

<a id="access-is-a-list-not-a-switch" />

## Sharing uses grants

Access is a set of additive **grants**, each one naming an audience, a set of capabilities, the paths it covers, and which published target it applies to. A matching grant admits a visitor. Revoking one grant does not revoke other matching grants or remove the owning team's permissions.

Grants let a Space be public at `/docs/**` and closed everywhere else. Revoking a share link takes effect on the next request, without a publish.

The dashboard covers the common cases. The CLI and API can create any grant.

| Audience | Who it admits |
| --- | --- |
| `public` | Anyone on the web |
| `team` | Every member of the owning team |
| `person` | One invited person, by email |
| `link` | Whoever holds a share link |
| `password` | Whoever knows a password |
| `machine` | Whatever holds a bearer token |
| `external` | An identity from a connected SSO or signer connection |

## Roles

A role is a named bundle of capabilities. Every grant carries one.

| Role | Can |
| --- | --- |
| `viewer` | View pages |
| `commenter` | View, read comments, write comments |
| `editor` | The above, plus publish |
| `manager` | The above, plus manage access |

Anyone can forward a share link or password, so they're limited to `viewer` or `commenter`.

## In the dashboard

Open the Space and go to **Share**.

The **General access** card holds a segmented control with two options:

| Option | What it does |
| --- | --- |
| **Private** | "Your team and people you add can view it." |
| **Public** | "Anyone on the web can open it." |

When the Space is public, a second control, **What public visitors can do**, sets their role. The other cards are **Password**, **Share link**, and **People**. A share link lets anyone with the share link open the Space without an account. Machine credentials, SSO, and path rules sit under **Advanced**. A Space with path-scoped rules says so in the General access caption and points you to the path rules under Advanced.

## Make a Space public

```bash
sf share grant --to public --role viewer --path '/**' --target live --space my-site
```

Scope it instead of opening everything:

```bash
sf share grant --to public --role viewer --path '/docs/**' --exclude '/docs/internal/**' --space my-site
```

`--to team` does the same for the owning team. Patterns use `*` for one segment and `**` for zero or more. A grant takes up to 100 include patterns and 100 excludes.

A public grant cannot carry publish or manage capabilities.

Grants default to `live`. Opening the live Space does not open branch previews or version URLs. To make immutable version URLs public too, add a grant for `all-versions`:

```bash
sf share grant --to public --role viewer --path '/**' --target all-versions --space my-site
```

Use `version:<id>` to open only one version. Branch previews need a `branch:<name>` grant; `all-versions` does not cover them or the live Space. A team grant admits the owning team; it cannot name another team you belong to.

## Share links

A new team-owned Space does not create a share link in the current CLI or dashboard. The owning team signs in at the live URL. Create a link when you want to share outside the team.

Team requests to `POST /v1/spaces` that do not send `capabilities: ["optional_access"]`, such as older CLI versions and dashboard tabs, still receive a compatibility Open link. Team Spaces created by current publish clients get no automatic link. Team requests that send the capability get no link, and their successful receipt can omit `access`. Anonymous Spaces keep their expiring Open link.

A share link is a lasting URL that opens only the paths you scoped it to, with no account needed. The secret is in the query string, so the link goes straight to the page:

```text
https://my-site.view.fast/docs?__=sfl_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

One request returns the page, with no redirect or interstitial, so `curl`, agents, and browsers all get the same page.

### Create one

```bash
sf share link create \
  --space my-site \
  --name "Client review" \
  --landing /docs \
  --path '/docs/**' \
  --path '/assets/**' \
  --exclude '/docs/internal/**' \
  --role commenter \
  --expires 7d
```

| Flag | Default | What it does |
| --- | --- | --- |
| `--name` | required | The name shown in the links list |
| `--landing` | `/` | The clean route the link opens at. It has to be inside the link's paths |
| `--path` | `/**` | An included pattern. Repeat for disjoint subtrees |
| `--exclude` | none | An excluded pattern, local to this link |
| `--role` | `commenter` | `viewer` or `commenter` |
| `--target` | `live` | `live`, `all-versions`, `version:<id>`, or `branch:<name>` |
| `--not-before` | none | Do not admit anyone before this timestamp |
| `--expires` | never | A duration such as `30m`, `24h`, `7d` |
| `--max-uses` | unlimited | Successful opens before the link stops working, 1 to 1,000,000 |
| `--require-verified-email` | off | Admit only visitors whose session has a verified email |
| `--network` | none | An allowed IP address or CIDR. Repeatable |
| `--country` / `--exclude-country` | none | Allowed or blocked ISO country codes |
| `--exclude-user-agent` | none | Block user agents containing this text |

In the dashboard, the **Share link** card's **Create share link** button opens a sheet with the same fields, labelled **Name**, **What link holders can do**, **What the link opens**, **Opens at**, **Paths**, **Starts**, **Expires**, **Maximum opens**, and a **Require a verified email** toggle.

### List, copy, revoke

```bash
sf share link ls --space my-site
sf share link copy lnk_xxxxxxxx --space my-site --show-secret
sf share link revoke lnk_xxxxxxxx --space my-site
```

Listing links never returns the secret. Only callers who can manage the Space's access can get the URL, and in a non-interactive shell you need `--show-secret` to print it.

Revoking a link removes its grant, so every copy of the URL stops working on the next request.

`sf share link edit` changes a link's scope, role, target, and constraints without changing its URL, so you can narrow a link you already sent instead of replacing it.

A Space that has not been claimed yet may keep up to 50 active links, and further creates return `anonymous_share_link_limit`.

## Passwords

A password is its own grant with its own scope, not a lock on the whole Space. You can have several named passwords, each covering different paths.

```bash
sf share password create \
  --space my-site \
  --name "Beta testers" \
  --path '/**' \
  --role viewer \
  --password-from-stdin
```

Pass the value on stdin, or through `SPACEFAST_SHARE_PASSWORD`. It never goes into `sf.jsonc`. The verifier is Argon2id.

```bash
sf share password ls --space my-site
sf share password rotate pwd_xxxxxxxx --space my-site --password-from-stdin
sf share password revoke pwd_xxxxxxxx --space my-site
```

Rotating keeps the grant and its scope, and immediately signs out sessions that used the old password. Revoking removes the grant, so those sessions lose access too.

The dashboard's **Password** card has **Set password**, **Change**, and **Remove**, with **Expires**, **Paths**, and **What password holders can do** under **Password options**. It manages one password. Use the CLI or API for more.

## Inviting people

```bash
sf share people invite person@example.com --space my-site --role commenter --scope /docs
sf share people ls --space my-site
sf share people remove person@example.com --space my-site
```

`--scope` defaults to `/` and is repeatable, so one invitation can grant the same role on several subtrees. `--target` picks what they get, defaulting to `live`.

In the dashboard, the **People** card takes an email, a **What they can do** role, and a **What they get access to** scope. Pending rows show **Invitation pending** with **Resend** and **Remove** actions.

A person can hold up to 32 scoped grants on one Space, so one collaborator can have different roles on different subtrees.

## Machine credentials

For a script or a job, issue a bearer token rather than sharing a link:

```bash
sf share token create --space my-site --name "Nightly export" --path '/exports/**'
sf share token ls --space my-site
sf share token rotate mch_xxxxxxxx --space my-site
sf share token revoke mch_xxxxxxxx --space my-site
```

The token is shown only once, right after you create it. Rotating keeps the grant and its scope and stops the old token from working immediately.

## Access requests

A visitor who lands on a Space they cannot open can ask for access. Requests show up in the **Access requests** card and in the CLI:

```bash
sf share request ls --space my-site
sf share request approve arq_xxxxxxxx --space my-site
sf share request deny arq_xxxxxxxx --space my-site
```

Approving invites the requester to the path they asked about.

## What a visitor sees

**On a public Space**, the page loads with no access check.

**With a share link**, the token is checked before the file is read, so the first request returns the page. The response is never cached. It also carries `Referrer-Policy: no-referrer`, so the secret does not leak through the referrer header on outbound clicks.

**On a protected Space with no proof**, the request answers **403** with the Space's access page and `Cache-Control: private, no-store`. The page offers whichever lanes you configured: a password box, an email code, a request-access form, or a sign-in with a Spacefast account.

**Signing in** sends the visitor to Spacefast and back to the page they originally asked for.

**Submitting a password** posts it from the same origin, and Spacefast checks it. On success, it sets the visitor's session cookie and sends a **303** back to where they were. Passwords are capped at 1024 bytes. Failures come back as rate limited, invalid password, or exchange unavailable.

A visitor session expires after 7 days without use, or 30 days after it started.

Two behaviors can look like bugs. A rewrite can't widen access: the visitor needs access to both the URL they asked for and the path it rewrote to. And a directory listing on a protected Space leaves out entries the visitor can't open.

## Revoking everything at once

```bash
sf access sessions revoke --space my-site
```

This ends every active visitor session on the Space, whatever admitted them: share link, password, private open, or signed-in account. It takes effect immediately, without a republish. Grants stay in place, so anyone with a valid link or password can open the Space again on their next visit. To stop a link or password from working, revoke its grant.

## Defaults for new Spaces

A team chooses the starting access for its new Spaces. In the dashboard, open team settings and go to **Access**.

| Preset | New Spaces start with |
| --- | --- |
| `private` | Access for the owning team |
| `public` | Access for the owning team, plus view access for anyone on the web |

The default is `private`. The API accepts the legacy value `team` and normalizes it to `private`. Changing the default applies only to Spaces created after the change. Neither preset creates a share link on its own.
