title: Versions and the live channel
description: Immutable versions, the live channel, promotion policies, and rollback to a retained ready version
---

A rollback points `live` back at a retained, ready version and doesn't rebuild it. By default it applies your current rewrites, which makes a new version from that version's files. Deleted or expired versions cannot be rollback targets.

## A version is a snapshot

A publish that changes files creates a version, an immutable snapshot of those files and the config they finalized with. Nothing modifies a version after it is ready. A publish with no changes can return `noop_publish` without creating a version.

IDs are `ver_` plus 32 hex characters. Once a version reaches `ready` it also gets a number, and the CLI and dashboard call it by that number.

```text
ver_4b81f0c2d9a7431e8c6d05fa27b3e914   v7
```

Numbers are handed out in the order versions become ready, not the order they were started. Two publishes racing each other get two distinct numbers, and a version that never reaches ready never takes one.

## States

| State | What it means |
| --- | --- |
| `created` | The manifest is declared, bytes are still expected |
| `uploading` | Bytes are landing |
| `uploaded` | Every declared file arrived |
| `finalizing` | The version is being compiled into its served form |
| `ready` | Ready to serve, numbered, and promotable |
| `failed` | Finalize or the build that fed it failed |
| `canceled` | Stopped before it finished |
| `expired` | A draft that ran out of time before finalize |

The path is `created`, `uploading`, `uploaded`, `finalizing`, `ready`. `failed`, `canceled`, and `expired` are terminal, and so is `ready`. A version produced by a remote build reports the build's own progress on the Build, not here. See [Frameworks and builds](/guides/frameworks).

## The live channel

A channel is a named pointer from the Space to one version. `live` is the only channel today, and it is the one visitors follow. Your default hostname and every custom domain serve whatever `live` points at right now.

A channel has a promotion policy.

| Policy | What a publish does |
| --- | --- |
| `auto` (default) | Finalizing a version moves the pointer to it |
| `manual` | The version becomes ready and the pointer stays put |

On a manual channel an ordinary publish comes back with `activation.outcome` of `unpromoted` and `reason` `channel_promotion_manual`. Nothing failed. The version is ready and waiting for an explicit promote.

```bash
sf channels list --space docs
sf channels set live --promotion manual --space docs
```

For staging workflows, preview publishes, and channel promotion history, see [Channels and previews](/channels).

## Promote and roll back

Promoting points `live` at a ready version. A newer version goes live as saved. An older one is a rollback: by default it applies your current rewrites to that version's files, which makes a new version and puts that live. Pass `--no-refresh-rewrites` (API: `refreshRewrites: false`) to make the older version live exactly as saved. Either way, the previous version keeps its own URL.

Rolling back is the same operation, pointed at an older version.

<Tabs>
<Tab title="CLI">

```bash
sf versions list --space docs
sf rollback v12 --space docs
sf promote v14 --space docs
```

Both take a version ID, a ref such as `v12`, or a bare number. Both wait for the pointer to settle by default. Pass `--no-wait` to get the operation handle back immediately.

</Tab>
<Tab title="Dashboard">

Open **Versions**, find the row, and hit **Make live**. Confirm on **Make v12 live?**. The Overview page carries the same action as **Roll back to** next to the previous version.

Afterward, the list shows the rollback state, for example *Rolled back from v13. Make it live below to roll forward.*

</Tab>
<Tab title="API">

```bash
curl -X POST \
  https://api.spacefast.com/v1/spaces/spc_9f2c.../versions/ver_4b81.../promote \
  -H "Authorization: Bearer sfa_xxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"channel":"live"}'
```

[`promoteSpaceVersion`](/api/reference/versions/promotespaceversion) waits by default and returns the version plus an operation handle. Add `?async=1` to get the handle without waiting. `channel` defaults to `live`, and any other name is rejected with [`channel_unsupported`](/errors/channel_unsupported).

</Tab>
</Tabs>

An explicit promote is never held by a manual policy. That hold only applies to promotions a publish asked for implicitly.

## Per-version URLs

Every version that reaches ready gets a fixed hostname of its own, computed once and stored. It serves that snapshot while the version is retained:

```text
https://my-space--v7.space.fast/
```

It serves that exact snapshot no matter what is live, and it survives a rename, a transfer, and any number of rollbacks. The API reports it as `immutableUrl`, with `immutableUrlStatus` of `pending` until the hostname is routable.

A version published from a connected Git branch also gets a branch hostname, `https://my-space--br-<alias>.space.fast/`, which follows the branch rather than the snapshot. The dashboard shows it on the version page as **Branch preview URL**. Existing Spaces stay on `view.fast`, and existing version and branch URLs retain their format. Full hostname rules are on [URLs and hostnames](/urls).

## Drafts expire in 24 hours

A version that is declared but never finalized is a draft. Drafts live for 24 hours. Past that they flip to `expired` and stop accepting uploads, so an abandoned draft cannot be resumed. Publish again instead. The expired draft stays in the version history.

This only affects versions still in `created`, `uploading`, or `uploaded`. A ready version has no clock on it.

## How many versions are kept

All of them. Ready versions stay until you delete them, on every plan.

To delete one:

```bash
sf versions delete v12 --space docs
```

A version the `live` channel points at cannot be deleted, and neither can one a branch hostname serves. Promote something else first. The refusal is `version_in_use` and names what is holding it.

## Stored config source

When `sf publish` or a remote build packs a version from `spacefast.config.ts`, the CLI evaluates the file into `sf.jsonc` and also stores the authored TypeScript config inside the version as `.spacefast/config-source.ts`. At finalize, the version records which config file produced it (`file`, `format`, `sourceSha256`, `evaluatedSha256`, and `compatibilityDate`).

`.spacefast/config-source.ts` is never served to visitors. Your team can read it alongside the version's uploaded files. Because `spacefast.config.ts` is also part of your source repository, enabling [source sharing](/git#source-sharing) lets anyone read it on the repository's `main` branch. Keep credentials and internal URLs out of `spacefast.config.ts` and read them from [Environment variables](/environment-variables) instead. The first time you publish with `spacefast.config.ts` to a Space whose source is available, `sf publish` warns you once.

## Compare what you uploaded with what is served

A version stores two representations of every path. `uploaded` is the byte you sent, before any transform. `served` is the immutable byte the version answers with. They differ where Spacefast processes a file. Private inputs such as `sf.jsonc` and `.spacefast/config-source.ts` exist in `uploaded` and are absent from `served` entirely.

[`listSpaceVersionFileLinks`](/api/reference/versions/listspaceversionfilelinks) mints short-lived read links for up to 200 paths at a time and takes `view=uploaded` or `view=served`. Fetch the same path both ways and diff them.

```bash
curl "https://api.spacefast.com/v1/spaces/spc_9f2c.../versions/ver_4b81.../files/links?path=index.html&view=served" \
  -H "Authorization: Bearer sfa_xxxxxxxxxxxxxxxxxxxxxxxx"
```

Link minting does not check whether the version holds the path. A path missing from the view you asked for fails as `version_file_not_found` when you follow the link.

To browse rather than diff, [`listSpaceVersionFiles`](/api/reference/versions/listspaceversionfiles) lists one version's files and [`listSpaceFiles`](/api/reference/spaces/listspacefiles) lists whatever `live` currently serves. In the dashboard, **Code** browses any version, with `?version=` pinning an older one.
