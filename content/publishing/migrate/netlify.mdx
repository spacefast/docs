---
title: Netlify
description: How to move a static site from Netlify to Spacefast.
---

Most Netlify sites that build to static files move directly: run the same build,
publish the output directory, and keep root `_redirects` and `_headers` files in
that output. Spacefast supports redirects, rewrites, external `200` proxies,
forced rules, query matching, custom `404` rules, conditions, supported response
headers, and Basic Auth. Check the target team's [routing
entitlements](/account/limits) before relying on gated features.

```text
# _redirects
/old /new 301
/app/* /index.html 200
/api/* https://api.example.com/:splat 200
```

## Migration checklist

- Confirm the Netlify publish directory, run the same build command, and publish that generated directory — or [connect the repo](/publishing/git) and Spacefast runs the build on every push.
- Make sure `_redirects` and `_headers` are present in the generated output, not only in the source tree.
- Move routing or header rules from `netlify.toml` into root `_redirects` and `_headers`.
- Recreate Netlify deploy-context environment variables in the system that builds your Spacefast artifact.
- Publish to a test space first. Every publish is an immutable version, your live site stays up during the switch, and rollback is always one click.

## What carries over

- Root `_redirects` and `_headers` files.
- External proxy rules written as absolute-URL `200` rewrites when enabled for
  the target team.
- Forced rules, splats, placeholders, exact query matching, custom 404s, and supported response headers.
- `_headers` Basic Auth when enabled for the target team.
- Static framework output from Astro, Eleventy, Hugo, Vite, [static Next.js exports](/publishing/frameworks/nextjs), and similar build tools when the generated files do not need a Netlify runtime.

## What to change

- Write explicit `301` statuses for permanent redirects; Spacefast defaults omitted statuses to `302`.
- Move `netlify.toml` redirects and headers into root `_redirects` and `_headers`.
- Replace Netlify Functions, Edge Functions, Identity, signed proxy redirects, and `Role` conditions before publishing protected content.

## Limitations

Spacefast hosts static artifacts and supports static routing conventions. It does not run Netlify's platform runtime. Audit these features before switching DNS:

- Netlify Functions, Background Functions, Scheduled Functions, Edge Functions, SSR pages, and framework adapters do not execute. Replace them with static generation, client-side calls to an external API, or a separate backend.
- Netlify Forms, Identity, role-based redirects, Split Testing, Visual Editor workflows, Netlify Blobs, Netlify DB, Image CDN transforms, Large Media, and post-processing features do not transfer. Spacefast's [image acceleration](/spaces/image-acceleration) uses Site Accelerator API URLs, not Netlify's `/.netlify/images` API.
- Build plugins, build hooks, and deploy-context variables are Netlify-specific and do not transfer. Deploy Previews and branch deploys have direct equivalents: [connect the repo](/publishing/git) and Spacefast builds on every push — production-branch pushes go live, other branches get preview URLs, and pull requests get a preview comment and a status check.
- Redirect features that only exist in `netlify.toml`, such as signed proxy redirects and custom proxy request headers, are not implemented. External `200` proxy rules work, but Netlify-specific signing and injected upstream headers do not.
- Header behavior is static. Do not rely on functions, edge functions, or proxied upstreams to receive headers from `_headers`; return those headers from the upstream service instead.
