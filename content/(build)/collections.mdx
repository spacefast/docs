Collections add structured content, custom tables, localization, and an admin editor to any Space. Declare them under `app` in `spacefast.config.ts`, and Spacefast backs them with your Space's database on publish.

## Define collections in `spacefast.config.ts`

Configure your app under the `app` block in `spacefast.config.ts` with `defineConfig`. A standalone `spacepress.config.ts` may sit beside it, but publish only one app definition per project (either inline under `app` or in `spacepress.config.ts`, not both). See [Configuration](/config-file).

The following configuration defines a `posts` collection, a `subscribers` table, an admin screen, authentication settings, and two locales:

```ts spacefast.config.ts
import { defineConfig } from "spacefast/config";

export default defineConfig({
  name: "my-space",
  app: {
    collections: {
      posts: { label: "Posts", title: "title" },
    },
    tables: {
      subscribers: { columns: { email: "text" } },
    },
    admin: { enabled: true, title: "Editorial" },
    auth: { enabled: true },
    locales: { default: "en", supported: ["en", "es"] },
  },
});
```

The `app` block accepts these keys:

| Key | Type | What it configures |
| --- | --- | --- |
| `name` | string (1–128 chars) | Optional app display name |
| `collections` | record of objects | Structured content collections with admin screens and query access |
| `tables` | record of objects | Custom relational tables in the Space's database |
| `actions` | record of objects | Server actions and form handlers; see [Actions and forms](/actions) |
| `pages` | record of objects | App page definitions |
| `routes` | object or array of objects | Custom application routes |
| `admin` | boolean or `{ enabled, path, title }` | Admin interface toggle, path, and title |
| `auth` | `{ enabled, providers, roles, twoFactor }` | App authentication settings and role definitions |
| `locales` | `string[]` or `{ default, supported }` | Supported locales and default locale |
| `plugins` | array or object | App plugin entries |

## How content is stored

Spacefast stores live collections and tables in your Space's dedicated MySQL database. You do not provision or manage a connection string.

- Inspect any table and read or edit rows by primary key with `sf db tables` and `sf db rows`. See [Database](/database).
- Preview versions use an isolated SQLite database per version, seeded from that version's code on its first request. Edits made in a preview never touch live data.
- Promoting a preview version initializes it against the live MySQL database before switching traffic.
- Owning team members keep their live Space role when administering a preview version.

## Read collections from Workers

When a Space runs both an app and a [Worker](/functions), Spacefast injects `env.APP` into the Worker handler. Use `env.APP.collection(name)` to read and write records from a Worker route while forwarding the visitor's session cookie.

This route lists published posts from the `posts` collection:

```ts functions/api/posts.ts
export async function GET(request: Request, { env }: { env: any }) {
  const posts = await env.APP.collection("posts").list({ limit: 10 });
  return Response.json(posts);
}
```

`env.APP.collection(name)` exposes five methods:

| Method | Request | Returns |
| --- | --- | --- |
| `list(params?)` | `GET` | Collection list payload |
| `get(id, params?)` | `GET` | One record, or `null` on `404` |
| `create(data)` | `POST` | Created record |
| `update(id, data)` | `PATCH` | Updated record |
| `delete(id)` | `DELETE` | Delete response |

`env.APP.query(path, params)` runs a `GET` query against the app's REST namespace, and `env.APP.fetch(path, init)` forwards arbitrary `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, or `DELETE` requests to the app runtime.

## Admin editor and Content API

Spacefast exposes API endpoints for launching the content editor, calling the Space's REST API, reading media attachments, and reconciling synced content.

| Operation | Route | What it does |
| --- | --- | --- |
| [`launchSpaceContentAdmin`](/api/reference/spaces/launchspacecontentadmin) | `POST /v1/spaces/{spaceId}/content/admin-session` | Creates a one-use editor launch URL (session cookie auth; optional `screen` or `path`) |
| [`createSpaceContentAdminLink`](/api/reference/spaces/createspacecontentadminlink) | `POST /v1/spaces/{spaceId}/content/admin-link` | Creates a one-use sign-in link expiring in 10 minutes (`spaces:write`, signs in the person behind the credential) |
| [`requestSpaceContentRest`](/api/reference/spaces/requestspacecontentrest) | `POST /v1/spaces/{spaceId}/content/rest` | Sends a relative REST request as the authenticated actor (`spaces:read` for reads, `spaces:write` for mutations) |
| [`getSpaceContentMedia`](/api/reference/spaces/getspacecontentmedia) | `GET /v1/spaces/{spaceId}/content/media/{attachmentId}` | Returns private attachment bytes (`Cache-Control: private, no-store`); optional `size` query |
| [`getSpaceContentSyncStatus`](/api/reference/spaces/getspacecontentsyncstatus) | `GET /v1/spaces/{spaceId}/content/sync` | Lists acknowledged source changes, conflicts, and associated build status |
| [`getSpaceContentSourceConflict`](/api/reference/spaces/getspacecontentsourceconflict) | `GET /v1/spaces/{spaceId}/content/sync/{bindingId}` | Compares common base, source, and live document revisions |
| [`resolveSpaceContentSourceConflict`](/api/reference/spaces/resolvespacecontentsourceconflict) | `POST /v1/spaces/{spaceId}/content/sync/resolve` | Saves the chosen revision when neither side has moved, then queues a commit and build |
| [`convertSpaceContentSource`](/api/reference/spaces/convertspacecontentsource) | `POST /v1/spaces/{spaceId}/content/conversions` | Converts a code-authored document to editable blocks while keeping the original in history |

For full request schemas and reconciliation routes (`reconcileSpaceContentSync`, `acknowledgeSpaceContentSync`), see the [API reference](/api/reference).

## CLI commands

Validate your configuration offline, inspect app environment variables, and run allowlisted maintenance commands from the CLI:

```bash
sf check
sf dev
sf app env
sf app wp option get blogname
sf app wp cache flush
```

- [`sf check`](/cli/reference#sf-check-dir) validates `spacefast.config.ts` (or `sf.jsonc`), app schema, routing rules, Worker routes, and scans publishable files for leaked secrets in one offline pass. It exits `2` when any check fails.
- [`sf dev`](/cli/reference#sf-dev) starts local frontend and Worker dev servers in the project. `sf dev` does not start a local preview for inline `app` configurations yet; publish to a preview channel to test app routes and admin screens end to end.
- [`sf app env`](/cli/reference#sf-app-env) prints scoped app environment variables with secrets masked by default. Pass `--reveal` to print plaintext values or `--format dotenv` for dotenv output.
- [`sf app wp`](/cli/reference#sf-app-wp) runs allowlisted WP-CLI commands against the Space (or against a local install with `--local` or `--path`). Read/inspect commands, safe maintenance (`cache flush`, `rewrite flush`, `cron event run`), and `spacepress *` are allowed. Spacefast refuses `eval`, `shell`, `db`, `config`, and `plugin install`. Remote runs return `output: null` because the runtime exposes no stdout channel.
- [`sf pages`](/cli/reference#sf-pages) manages custom Spacefast system and error page templates (`_pages/*.html`), not CMS collections. See [Customization and error pages](/customization).
