There's no dashboard editor for crons. Declare schedules in `sf.jsonc`, then publish and make that version live to apply them. A preview does not replace the live version's schedules.

## How a run happens

A cron is a scheduled `GET` against a path on your own site. It goes through the same front door a visitor gets, so whatever serves that path answers it: a [Zero](/zero-runtime) endpoint, a [Functions](/functions) route, or a static file.

A response under 400 is a success and is silent. A response of 400 or worse, or a fatal error, is a failure and is reported.

| Rule | Behavior |
| --- | --- |
| Timing | Fires approximately on schedule, on the provider clock, jittered. Real fire times are never surfaced |
| Overlap | Still running when the next fire comes? That fire is skipped, not queued |
| Concurrency | 3 runs at once, at most |
| Run ceiling | 8 hours per run |
| Retries | None. The next fire is the retry |

## Declare it

There is no write API and no dashboard editor. `sf.jsonc` is the only writer, and a publish is the only edit. That is what makes a rollback restore the previous schedules for free, placed against your current allowance.

```jsonc sf.jsonc
{
  "crons": [
    { "path": "/api/digest", "schedule": "daily" },
    { "path": "/api/poll", "schedule": "*/15 * * * *" }
  ]
}
```

```bash
sf publish
sf crons ls
```

Validation is blocking. A bad cron fails the publish rather than shipping a schedule that never fires.

## Schedule syntax

Three grammars in two kinds. Named and shorthand schedules are **simple** crons. Five-field crontab schedules are **advanced** crons, and your plan sets how many of each a Space runs.

| Kind | Examples | Notes |
| --- | --- | --- |
| Named (simple) | `hourly`, `daily`, `twicedaily`, `weekly` | The provider picks the moment |
| Shorthand (simple) | `3h`, `2d`, `1w` | `N` runs per hour, day, or week: `3h` runs three times an hour. Up to 12 an hour, 23 a day, 6 a week |
| Crontab (advanced) | `30 16 * * 1-5`, `*/15 * * * *` | Five numeric fields, down to every minute |

Crontab fields are minute `0-59`, hour `0-23`, day of month `1-31`, month `1-12`, weekday `0-7`. Lists (`1,15`), ranges (`1-5`), `*`, and a `/step` over a span are supported.

There are no `@daily` macros and no month or day names. `@daily` and `mon` are rejected.

Your schedule string is stored verbatim and never normalized.

## Paths

| Rule | Value |
| --- | --- |
| Shape | Starts with `/`, matching `/^\/[^*:?#\s\\]*$/` |
| Length | 512 characters |
| Not allowed | Query strings, fragments, `*` splats, `:placeholders` |
| Substitution | `{{ vars.NAME }}` resolves when the version publishes |
| Requirement | At least one letter or digit after slug normalization |

Each entry gets a **key** derived by slugging its path. `/api/cron/digest` becomes `api-cron-digest`. Two paths that slug to the same key are rejected at publish.

## Allowance by plan

Each Space runs a set number of simple and advanced crons, by plan:

| Plan | Simple | Advanced | With Boost |
| --- | --- | --- | --- |
| Free | 1 | 0 | No Boost. Upgrade the plan |
| Go | 5 | 0 | 25 simple, 5 advanced |
| Plus | 10 | 5 | 30 simple, 5 advanced |
| Enterprise | 50 | 25 | No Boost |

Boost is a per-Space add-on on Go and Plus. It adds 20 simple crons and raises advanced crons to at least 5, so on Plus it adds simple crons only. Free has no Boost: upgrading the plan is the way to more crons.

Each cron takes a slot of its own kind, in the order you declare them. A later crontab can still take an advanced slot after an earlier simple cron ran out of simple slots:

- A crontab takes an advanced slot while one is left.
- A crontab with no advanced slot left still publishes, with a warning. It runs at its closest simple schedule and counts against the simple allowance. That can run more or less often than the crontab asked, and not at the times it names: `*/5 * * * *` runs `12h` (12 times an hour), and `0 9 * * 1-5` runs `5w` (5 times a week, not necessarily on weekdays at 9:00).
- Crons past the allowance still publish, and the publish carries a warning. Within each kind of slot, the first ones declared run. The rest show as not scheduled, "over this plan's cron limit", on the dashboard's **Crons** page and in `sf crons ls`.

Advanced crons also run at their closest simple schedule for now, until advanced scheduling is enabled for the platform.

A raised limit applies right away. After an upgrade or Boost, crons that were waiting start running without a publish.

A lowered limit applies at your next publish, promote or rollback. Until then, a downgrade or Boost ending changes nothing: crons that are running keep running.

For now, whatever the plan, a Space can declare at most **8** crons, and past that the publish fails validation. That ceiling rises to the plan limits above as the runtime update reaches every box.

## List and trigger

```bash
sf crons ls
sf crons run api-cron-digest
sf crons run /api/digest --header "authorization: Bearer $CRON_SECRET"
```

`sf crons run` takes a key or an exact path, and the argument is required. A leading `/` is slugged to a key first. An unknown target exits `20` with `cron_not_found`.

`--header` repeats and takes `name: value`. A value with no colon, or a colon at position zero, exits `2`.

The run prints a receipt with the URL, status, duration, content type, byte count, and a 200-character body preview. An HTTP status of 400 or worse exits `1` with `cron_run_failed` and the whole receipt as details.

:::note
`sf crons run` cannot send the platform's own `x-spacefast-cron` header. A handler that gates on it will refuse a manual run, which is why the example above passes a shared secret explicitly.
:::

Before the first publish, `sf crons ls` prints:

```text
No scheduled jobs declared. Add a `crons` block to sf.jsonc.
```

## Failures

The dashboard's **Crons** page and `sf crons ls` both report recent failures per cron, plus failures that could not be attributed to one. A failure carries the time it occurred, an exit code when there is one, and a reason when the provider gave one. Some rows read only "no detail", which means the provider said only that it failed.

Run output is never echoed. A response body can carry secrets and response data, so it is not stored.

Only the newest failures are kept, with no history behind them. A real failure and a skipped overlap are stored identically today, so read a row as "this fire did not complete".

## API

[`listSpaceCrons`](/api/reference/spaces/listspacecrons) is `GET /v1/spaces/{spaceId}/crons`. It returns the version the schedules came from, which is `null` before the first publish. Each entry carries its key, path, schedule, and recent failures, plus:

| Field | Meaning |
| --- | --- |
| `scheduled` | Whether the cron runs |
| `tier` | `simple` or `advanced`. `null` when not scheduled |
| `runsAs` | The schedule that actually runs. `null` when not scheduled |
| `reason` | `over_plan_limit` past the allowance, `unsupported_schedule` for a schedule that cannot run. `null` when scheduled |

The response's `allowance` carries the Space's `simple` and `advanced` counts and `upgrade`, the step that unlocks more: `upgrade_plan`, `upgrade_or_boost`, `boost`, or `null` when there is none.
