title: Environment variables
description: Set variables on a Space or a team, keep secrets write-only, substitute plain values at build time, and read them from Workers and app code

You can scope a variable to a single Space or to the whole team, and a Space-level value always wins over a team one with the same name.

## Two scopes

| Scope | Where you set it | Who sees it |
| --- | --- | --- |
| Space | `sf env`, or the Space's **Variables** page | That Space |
| Team | The team's **Variables** page | Every Space in the team |

A Space value wins over a team value with the same name. In the dashboard, the Space page adds a **Source** column and an **Override** action for a value inherited from the team.

Platform-provided `SPACEFAST_*` values also appear in reads, marked as system scope. They are read-only.

## Set, list, and remove

Manage Space variables from the CLI:

```bash
sf env set STRIPE_PUBLISHABLE_KEY pk_live_123
sf env set STRIPE_SECRET_KEY --value-from-stdin < ./key.txt
sf env list
sf env list --show-values
sf env remove STRIPE_SECRET_KEY
```

Pass the value as an argument or read it from stdin, never both and never neither. Stdin strips one trailing newline, and an empty stdin is an error.

Passing a secret on the command line prints a warning naming the variable, because it lands in your shell history. Prefer `--value-from-stdin`.

:::note[No republish needed for a Space variable]
A version keeps the values it was sealed with, so a write never edits the running version. Setting or deleting a Space variable queues a new version with the new values, and that version replaces the live one when it is ready. A team variable change does not queue one; it reaches each Space at that Space's next publish.
:::

## Secret or plain

Secret values are write-only. After creation, no API response, CLI output, dashboard field, log line, or activity entry returns one.

`sf env set` decides in this order:

1. An explicit `--secret` or `--no-secret` wins.
2. Otherwise the existing Space variable keeps its current classification.
3. Otherwise the new variable is **secret**.

A brand new variable with no flag is write-only. Pass `--no-secret` when you want to read it back later.

## Naming rules

| Rule | Value |
| --- | --- |
| Length | 1 to 128 characters |
| Pattern | `/^[A-Za-z_][A-Za-z0-9_]*$/` |
| Reserved | Names starting with `SPACEFAST_` |
| Empty values | Refused; a variable always has a value |

## Build time and runtime are separate

A plain variable reaches both stages. It is filled into template files when a version finalizes, and server code reads it at runtime. A secret reaches server code only. A template that references a secret is blocked with `secret_variable_in_template`.

### Build time, `{{ vars.NAME }}`

List files under `templates` in `spacefast.config.ts` (or your existing `sf.jsonc`). Every `{{ vars.NAME }}` token in those files is substituted when the version finalizes.

```ts spacefast.config.ts
import { defineConfig } from "spacefast/config";

export default defineConfig({
  templates: ["index.html", "config.json"],
});
```

Repository builds can take a different value per channel or branch:

```bash
sf env set API_URL https://api.example.com --production-value https://api.example.com
sf env set API_URL https://api.example.com --preview-value https://staging.example.com
sf env set API_URL https://api.example.com --branch-value beta=https://beta.example.com
```

`--branch-value` takes `branch=value` and repeats. An empty branch or an empty value is a validation error.

### Runtime variables

Server-only values belong in `.env.server` next to your project. `sf publish` reads that file, syncs every key into the Space's variables **as secrets**, and never uploads the file itself. The shared publish denylist covers `.env.*`, so the bytes stay on your machine.

```bash
cat > .env.server <<'EOF'
STRIPE_SECRET_KEY=sk_live_123
EOF
sf publish
```

A [Worker](/functions) reads variables from `env` (its second argument in `handler.ts`, or `context.env` in `functions/`):

```ts functions/api/charge.ts
export async function POST(
  request: Request,
  { env }: { env: { STRIPE_SECRET_KEY?: string } },
) {
  return Response.json({ configured: Boolean(env.STRIPE_SECRET_KEY) });
}
```

For Spaces running an app, run `sf app env` ([`sf app env`](/cli/reference#sf-app-env)) to inspect scoped app environment variables (secrets masked by default; pass `--reveal` for plaintext). Existing [Zero 0.8](/zero-migration) apps read the same values from `ctx.env`, and also accept `.env.lakebed.server` (which acts as the full Space-scope list and deletes omitted Space variables on publish).

An anonymous first publish, before you have an account, syncs nothing and reports `skipped: "anonymous"`.

#### Runtime caps

| Cap | Value |
| --- | --- |
| Keys | 64 |
| Name | 128 bytes |
| One value | 16 KiB |
| All values together | 64 KiB |
| Refused prefixes | `SPACEFAST_`, `ZERO_` |

## Pull, import, and template

Pull plain variables into a local dotenv file:

```bash
sf env pull
sf env pull .env.development --force
sf env pull --stdout --format json
```

`sf env pull` writes `.env.local` by default and refuses to overwrite an existing file without `--force`. The file is written with mode `0600` through a temp file and a rename. A pre-existing loose file gets tightened too.

Only non-secret values are pullable. Write-only names come back in `omittedWriteOnly` with a warning instead of a blank line. Team-scope values are written as `shared.<NAME>`.

Import variables from a dotenv file or another platform's export:

```bash
sf env import .env.production
sf env import .env --from vercel --no-secret
```

`sf env import` reads a dotenv file and sends one write per entry, in file order. It strips a BOM and a leading `export `, and skips blank and `#` lines. It requires quotes to close and strips inline `#` outside quotes. A later duplicate overwrites an earlier one. A missing `=` or an empty value is an error naming the line. `--from` accepts `dotenv`, `vercel`, `netlify`, and `cloudflare`.

Generate a dotenv template locally from existing platform configs:

```bash
sf env template
```

`sf env template` is offline and makes no API call. It reads `package.json`, `vercel.json`, `netlify.toml`, and `wrangler.toml` from a directory and writes a dotenv template of the names those platforms expect.

## Dashboard

Team variables live at **Variables** in the team navigation. Space variables live at **Variables** for the Space. The table columns are **Name**, **Value**, **Secret**, and, on a Space, **Source**.
