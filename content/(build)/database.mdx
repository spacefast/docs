Every provisioned Space gets its own MySQL database with no connection string to manage. Query it through SpacePress's typed ORM (`spacepress/server/db` and `db`), reach it over SQL from a [Worker](/functions) with `env.DB`, or inspect tables, edit rows, and open a single-use SQL console from the CLI, dashboard, and API.

## How a Space gets a database

A Space receives a dedicated MySQL database automatically once provisioned, with no extra setup or flag required.

- **SpacePress collections and SQL tables:** Declare `collection()` and `table()` schemas under `sp/` (or `app.collections` / `app.tables` in `spacefast.config.ts`) and query them through SpacePress's typed ORM. See [Collections and CMS](/collections).
- **Workers:** Every [Worker](/functions) receives `env.DB`, a D1-shaped SQL binding backed by your Space's MySQL through a broker, so no credentials or DSN ever enter your bundle.
- **Any provisioned Space:** `sf db tables`, `sf db rows`, and `sf db console` work against the Space's database on any runtime.
- **Isolated preview databases:** Preview versions run against an isolated SQLite database per version so preview writes never affect live MySQL data.

:::caution[There is no external connection string]
No route, flag, or dashboard field returns a database DSN. Your code reaches MySQL through SpacePress's ORM (`spacepress/server/db` and `db`) or `env.DB`. For direct SQL queries, open the single-use SQL console below.
:::

## Query from code

### Visitor-scoped SpacePress queries (`spacepress/server/db`)

Import your declared collections and tables from `"spacepress/server/db"` in pages, routes, queries, and mutations. Every call automatically enforces row-level access rules, draft visibility, and field-level `.access()` masks for the active visitor:

```ts sp/app/blog/page.tsx
import { posts } from "spacepress/server/db";

export default async function Blog() {
  const published = await posts.list({
    where: { tags: { has: "release" } },
    orderBy: { publishedAt: "desc" },
    with: { cover: true },
    limit: 20,
  });

  return (
    <ul>
      {published.map((post) => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}
```

When trusted server code needs to bypass visitor filters explicitly, call `.system` on the kind (for example, `posts.system.list({ limit: 100 })` or `posts.system.get(id)`).

### Trusted Drizzle-inspired ORM (`db`)

Inside server actions, hooks, and background jobs, you can also use the Drizzle-inspired `db` API to run typed queries and mutations directly:

```ts sp/app/page.tsx
import { db } from "spacepress";

export default async function Home() {
  const notes = await db.query.notes.findMany({ columns: { title: true }, limit: 5 });
  return <ul>{notes.map((note) => <li>{note.title}</li>)}</ul>;
}
```

For writes and single-row lookups inside `sp/` server modules (`import { db } from "spacepress/server"`):

```ts sp/tasks.ts
import { db } from "spacepress/server";
import { tasks } from "./schema";

const first = await db.query.tasks.findFirst({ where: { done: false } });
const [created] = await db.insert(tasks).values({ title: "Ship v1" }).returning();
```

### Direct SQL from Workers (`env.DB`)

In a [Worker](/functions), `env.DB` exposes the D1 query interface against your Space's MySQL database:

```ts functions/api/notes.ts
export async function GET(request: Request, { env }: { env: { DB: D1Database } }) {
  const { results } = await env.DB.prepare("SELECT * FROM notes LIMIT 10").all();
  return Response.json(results);
}
```

## Declarative access control, search, and migrations

### Role ladder and row-level filters

SpacePress evaluates access rules on an ordered role ladder: `guest < subscriber < author < editor < admin`. Naming a role admits that role and every higher role.

- **Shorthands:** `"anyone"`, `"authenticated"`, `"self"`, a role name, or a boolean.
- **Row-level filter functions:** Return a boolean or an access filter from `(ctx) => ...` (sync or `async`). Returning a filter compiles straight into SQL/PHP for `read`, `update`, and `delete` queries; non-matching rows answer `404`. Access functions may run read-only trusted queries (`db.query.<kind>`, `db.globals.<name>.get`, `<kind>.system`) to check memberships or grants; writes, outbound `fetch()`, mail, and jobs are refused inside access rules.
- **Field masks:** Chain `.access({ read, create, update })` onto any column to strip or refuse unauthorized fields across REST responses, pages, and client queries.

### Full-text search (`.searchable()`)

`list({ search })`, `count({ search })`, `?search=` on REST routes, `GET /search`, and `/wp/v2/search` match prefixes across searchable fields while keeping the list's sort order and enforcing every row and field access rule. By default, SpacePress searches title, content, and every `text()` or `richText()` column. Mark fields with `.searchable()` to restrict search to title, content, and the marked fields, or chain `.searchable(false)` to exclude any column (including title or content).

### Forward-only SQL migrations and retention

- **Migrations:** Commit each generated migration folder under `sp/_generated/migrations/`. SpacePress folds `ops.json` files in order and writes a new numbered migration folder whenever a `table()` schema changes. Removing a column or table retires it while preserving stored data.
- **Safe renames:** Keep physical SQL names intact with `.column("old_name")` and `storageName: "old_table"`, and accept old API field names with `.alias("oldName")`.
- **Soft deletes and revisions:** Configure `retention` (`"forever"` by default, or durations like `"30d"` and `keepLast`) and query soft-deleted rows with `deleted: "exclude" | "include" | "only"`.

## Inspect tables and rows

`sf db tables` and `sf db rows` work on any provisioned Space, regardless of runtime. They list your Space's tables and the tables your code created, excluding Spacefast's internal tables:

```bash
sf db tables
sf db rows list notes --limit 20
sf db rows list notes --where status=open
sf db rows add notes --data '{"title":"First note"}'
sf db rows update notes --key id=1 --set title="Updated note"
sf db rows delete notes --key id=1 --yes
```

- `sf db rows list` returns 1 to 100 rows per page (default 50) in primary-key order. Secret columns such as password hashes and session tokens read as `[redacted]`.
- `add`, `update`, and `delete` accept up to 50 rows in one transaction (either all changes apply or none do).
- Rows are editable only when the table has a primary key with no binary or secret column, uses InnoDB, and has no triggers. You cannot write to binary, generated, or secret columns.
- `sf db rows delete` prompts for confirmation; pass `--yes` for non-interactive runs. Deleted rows cannot be restored from the CLI.

All table and row endpoints require write access (`spaces:write`) and an authenticated API key or CLI login.

## Open the SQL console

When you need raw SQL, Spacefast mints a single-use phpMyAdmin sign-in URL and records the access in your Space's [activity log](/activity).

Open **Database** for the Space in the dashboard and select **Open db console**. From the CLI:

```bash
sf db console
sf db console --show-secret
```

`sf db console` opens a browser by default because the URL grants full SQL authority over the Space's database. `--show-secret` prints the URL instead, and the URL is masked in `--json` receipts unless you pass it.

## Backups and database exports

Spacefast takes automatic MySQL backups for every Space. Personal runs daily backups with a 7-day self-service restore window; Go runs hourly backups with 7-day restore; Pro and Enterprise run hourly backups with 30-day restore. See [Backups, archives, and exports](/exports) for full Space exports and restore details.

For Spaces running an existing [Zero 0.8](/zero-migration) capsule, `sf db export` walks every declared table in stable 500-row keyset pages through `GET /v1/spaces/{spaceId}/db/export` and writes one atomic JSON backup (`mode 0600`):

```bash
sf db export
sf db export docs --output ./docs-backup.json
```

Without `--output`, Spacefast writes `spacefast-backup-<space>-<timestamp>.json`. If the export fails part-way, any existing file at that path stays untouched.

## Legacy Zero 0.8 schema commands

The declared-schema commands (`sf db`, `sf db dump`, `sf db migrate`, and `sf db export`) apply only to existing [Zero 0.8](/zero-migration) capsules that declare a capsule schema. Running them against a Worker returns [`runtime_kind_mismatch`](/errors/runtime_kind_mismatch), and running them against a static Space returns [`db_not_available`](/errors/db_not_available). Use `sf db tables`, `sf db rows`, and `sf db console` instead for Workers and SpacePress apps.

```bash
sf db
sf db dump --table notes --limit 100
sf db migrate
```

- `sf db` inspects the live Zero 0.8 version's declared tables, schema hash, and pending migration plan (`--port` or `--local-url` targets a local `sf dev` loopback server).
- `sf db dump` reads 1 to 100 rows per declared table (default 25) through the live runtime.
- `sf db migrate` checks your local project configuration (`spacefast.config.ts` or `sf.jsonc`) before contacting the API, re-applies the live capsule's stored migration plan, and previews additive source changes.

## Limits

| Limit | Value |
| --- | --- |
| Databases per Space | 1 |
| `sf db rows list --limit` | 1 to 100, default 50 |
| `sf db rows` batch write (`add`, `update`, `delete`) | 50 rows per transaction |
| `sf db dump --limit` (Zero 0.8) | 1 to 100, default 25 |
| `sf db export` page size (Zero 0.8) | 500 rows, fixed |
