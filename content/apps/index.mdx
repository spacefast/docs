A space serves static files by default. Add a `runtime` block to `sf.jsonc`
when the version needs code as well. Two runtimes exist: [Zero](/apps/zero), a
full-stack runtime with a built-in database, authentication, and storage, and
[Functions](/apps/functions), a single Web-standard `fetch` worker beside your
static files. This page helps you pick one.

|                   | [Zero](/apps/zero)                 | [Functions](/apps/functions) |
| ----------------- | ---------------------------------- | ---------------------------- |
| You write         | Capsule: schema and named handlers | Worker: one `fetch` handler  |
| Database          | Built in                           | Optional `env.DB` binding    |
| Authentication    | Built in                           | Bring your own flow          |
| Storage           | Built in                           | Built in (`env.STORAGE`)     |
| Framework         | Zero client and server APIs        | Web APIs and npm packages    |
| Local development | `sf dev`                           | Your framework's dev server  |

Pick Zero when the database, authentication, and storage are the app. Pick
Functions when you already have a worker or an SSR build, or when you want
direct control over request handling.

The runtime block belongs to the version. The publish command compiles it with
the files. When you promote an older version, Spacefast restores its code and
runtime settings.

Both runtimes use the normal commands: `sf publish`, `sf runtime status`, and
`sf logs runtime --follow`. Each runtime page has its own quick start.
