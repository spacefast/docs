The project config holds the settings Spacefast reads when a version finalizes. Write it as `spacefast.config.ts` or as `sf.jsonc`. Both formats accept the same keys, and both stay supported. `sf init` writes `spacefast.config.ts`.

## File names and discovery order

The CLI looks for the config in the project directory. The first file found wins, in this order.

1. `spacefast.config.ts`
2. `sf.jsonc`
3. `spacefast.jsonc`
4. `spacefast.json`
5. `sf.json`
6. `.sf/sf.json`
7. `.sf/config.jsonc`
8. `.sf/config.json`

No other TypeScript or JavaScript file name is read. `spacefast.config.mts` and `spacefast.config.js` are ignored.

All eight files are private. They are never served.

## A full example

The two files below declare the same config.

import { defineConfig } from "spacefast/config";

export default defineConfig({
  // Which Space this project publishes to, and what it is called.

  name: "My App",

  // Serving shape.
  index: "index.html",
  fallback: { path: "index.html", status: 200 },
  cleanUrls: true,
  listing: false,

  // Listing, sharing, and browser icon metadata.
  meta: {
    title: "My App",
    description: "What this site is",
    image: "/og.png",
    favicon: "/favicon.ico",
  },

  // Visual tokens for Spacefast-authored pages (404, access, index).
  theme: { accent: "#0d9488", background: "#ffffff", name: "My App" },

  // Files that receive {{ vars.NAME }} substitution at finalize.
  templates: ["index.html"],

  // Analytics tags and custom snippets.
  superpowers: {
    googleAnalytics: { enabled: true, measurementId: "G-XXXXXXX" },
  },

  // Settings for builds the platform runs from a connected repository.
  build: {

    installCommand: "pnpm install",
    buildCommand: "pnpm build",

## TypeScript config

`spacefast.config.ts` is an ES module. Its default export is the config. The export can be an object, a promise of an object, or a function that returns either. An async function works.

```ts spacefast.config.ts
import { defineConfig } from "spacefast/config";
import { siteTitle } from "./site/meta";

export default defineConfig(async () => ({
  name: siteTitle,
  cleanUrls: true,
}));
```

The CLI bundles the file and its relative imports, then runs the bundle in its own process. Package imports and Node.js built-ins are not bundled. They resolve from the project directory when the config loads.

`sf build`, `sf publish`, and hosted Git builds load the config before they run the install command. Package imports other than `spacefast/config` must already be installed when the config loads. For a fresh checkout, use relative files, Node.js built-ins, and `spacefast/config` so the config does not depend on that install step.

The resolved value must be a JSON object. Strings, numbers, booleans, `null`, arrays, and plain objects are allowed. A key set to `undefined` is dropped. Any other value, for example a `Date`, fails the load.

The config is code. It runs on your machine and in hosted builds. Do not put secrets in it, because the resolved values are stored with the version.

### `defineConfig` and types

The CLI provides the `spacefast/config` module.

| Export | Kind | What it is |
| --- | --- | --- |
| `defineConfig` | function | Returns its argument unchanged. Its signature type-checks the default export |
| `SpacefastConfig` | type | The config object |
| `SpacefastConfigInput` | type | `SpacefastConfig`, a promise of it, or a function that returns either |

The CLI supplies the module when it loads the file, so the project needs no dependency for it.

:::note[Editor types]
The published `spacefast` package includes `spacefast/config` and its types. For editor type checking, add it as a development dependency with `npm install --save-dev spacefast`. The CLI supplies the helper when loading the config even without that project dependency.
:::

`defineConfig` is optional. A plain default export works the same way.

```ts spacefast.config.ts
import type { SpacefastConfig } from "spacefast/config";

export default { name: "My App", cleanUrls: true } satisfies SpacefastConfig;
```

## Precedence and failure rules

- The first file in the discovery order wins. The CLI prints a warning for each lower file it ignores.
- An explicit `--config` path skips discovery. The CLI reads that file only.
- The selected file must be valid. If it fails to load or validate, the command stops with `config_invalid` (exit 2). The CLI never falls back to a lower file.
- A selected file that exists but cannot be read also fails with `config_invalid`.
- A `--config` path that does not exist fails with `config_not_found` (exit 2).

A TypeScript file fails to load when it throws, has no default export, imports a package that is not installed, or resolves to a value that is not JSON. A file that loads but sets an invalid key fails validation. For example, `cleanUrls: "yes"` reports `spacefast.config.ts is invalid: cleanUrls: Expected a boolean`.

## Which commands read it

Every command that selects a Space from the current directory reads the config. That includes commands that take `--space`, so an invalid config stops them too. `sf publish`, `sf build`, `sf dev`, `sf doctor`, and `sf routing inspect` also read it for their own work. `sf doctor` reports the selected file and any ignored files on its `project-config` line.

Two command groups take an explicit path.

| Command | Flag | What it reads |
| --- | --- | --- |
| `sf git connect`, `sf git update`, `sf git build` | `--config=<path>`, env `SPACEFAST_CONFIG` | The `build` block, sent as repository build settings |
| `sf rules validate`, `sf rules test` | `--file=<path>` | The `firewall` and `cache` blocks |

## How the TypeScript config ships

The server does not run TypeScript. When `sf publish` or `sf build` packs a version, the CLI evaluates `spacefast.config.ts`. It writes the result into the version as `sf.jsonc`, in place of any `sf.jsonc` on disk. Your source files do not change.

Files that the config imports are ordinary files. If they are in the published directory, they are published and served.

Hosted Git builds run the same CLI build, so they evaluate a committed `spacefast.config.ts` too.

Loose-file publishing through the API or MCP does not evaluate TypeScript config. This includes local MCP publishing when a local directory becomes a file upload. If the upload includes `spacefast.config.ts`, it fails. Run `sf publish` from the project directory to evaluate the config, or run `sf build` and publish its `.spacefast/build-output.tgz` archive with `--prebuilt`. Sending the framework output directory alone does not carry the resolved project config.

## Migrate from sf.jsonc

Migration is optional. `sf.jsonc` stays supported. If the project uses another JSON file name, use that file in step 1.

1. Move `sf.jsonc` to `spacefast.config.ts` in the project directory.
2. Add `import { defineConfig } from "spacefast/config";` as the first line.
3. Put `export default defineConfig(` before the opening `{`.
4. Put `);` after the closing `}`.
5. Run `sf doctor`.
6. Make sure that the `project-config` line starts with `ok` and names `spacefast.config.ts`.

Quoted keys, `//` comments, and trailing commas are valid TypeScript. The pasted object needs no other change. The `$schema` key is allowed but has no effect in TypeScript. Your Space link in `.spacefast/space.json` does not change.

## File format

`sf.jsonc` and the other JSON names are JSON with comments. Point `$schema` at `https://spacefast.com/schemas/sf.json` for editor completion and validation. The schema covers the JSON files only.

The config is capped at 256 KiB. For `spacefast.config.ts`, the cap applies to the resolved JSON, not to the source file.

## Identity

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `$schema` | string | none | Editor pointer to the published JSON Schema |
| `space` | string | none | The Space this project publishes to, as a slug or an `spc_` id |
| `name` | string, 1 to 255 chars | none | Display name for the Space |

While `name` is set in the file, the API refuses to rename the Space. The file wins, so a rename means editing the file and publishing.

## Serving

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `index` | string or `false` | inferred, see below | The directory index file. `false` disables index resolution |
| `fallback` | string, or `{ path, status }` | none | The committed file served when no exact route matches. `status` is 100 to 599 |
| `cleanUrls` | boolean | `true`, unless a 200-status `fallback` is set | Serves `about.html` at `/about` |
| `listing` | boolean | on when no index could be inferred and the version runs no worker | Automatic directory listings |

`index` defaults to `index.html` when the version has one at the root. Otherwise, if the version publishes exactly one HTML file, that file. Otherwise, if there is exactly one HTML file at the root, that one. Otherwise `false`.

`"fallback": { "path": "index.html", "status": 200 }` is the SPA declaration. It names the shell that owns every unresolved route, so it also turns `cleanUrls` and `listing` off unless you set them yourself. A `fallback` path that is not a committed file fails the publish.

## Metadata and appearance

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `meta.title` | string, up to 300 chars | none | Title for listings, sharing, and the viewer |
| `meta.description` | string, up to 1000 chars | none | Description for the same |
| `meta.image` | string, up to 2000 chars | none | Sharing image |
| `meta.favicon` | string, up to 2000 chars | none | Browser icon |
| `theme.accent` | color | none | Accent color on Spacefast-authored pages |
| `theme.background` | color | none | Background color on the same |
| `theme.name` | string, 1 to 120 chars | none | Display name in the brand row |
| `theme.logo` | string, up to 2000 chars | none | An `https://` URL or a root-relative path |
| `theme.font` | string, up to 256 chars | none | A plain font-family stack. No `url()` or `src` |

Colors accept hex, `rgb()`, `rgba()`, `hsl()`, `hsla()`, and CSS color names. `theme` is a closed object, so an unknown key is an error.

A `theme.json` file next to the config is an inference input rather than configuration. Only `settings.color.palette` and `settings.typography.fontFamilies` are read from it. A [Zero](/zero-runtime) capsule's Tailwind compile reads the same file.

What these tokens paint, and how to replace those pages outright, is on [Layout, theme, and site pages](/site-pages).

## Templates

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `templates` | string array, up to 100 entries | none | Files whose `{{ vars.NAME }}` tokens are substituted at finalize |

See [Environment variables](/environment-variables) for where the values come from.

## Superpowers

Platform-managed script injection and your own snippets.

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `superpowers.enabled` | boolean | on unless set to `false` | Master switch for platform-managed injections |
| `superpowers.disable_all_injection` | boolean | none | When true, suppresses every managed injection |
| `superpowers.googleAnalytics.enabled` | boolean | none | Turns the tag on |
| `superpowers.googleAnalytics.measurementId` | string, up to 64 chars | none | The `G-` measurement id |
| `superpowers.googleTagManager.enabled` | boolean | none | Turns the container on |
| `superpowers.googleTagManager.containerId` | string, up to 64 chars | none | The `GTM-` container id |
| `superpowers.javascriptTags` | array, up to 16 entries | none | Custom snippets. Each has `code` (up to 8 KiB) plus optional `id`, `name`, `enabled` |

Injection is on unless `enabled` is `false` or `disable_all_injection` is `true`.

## Build

Settings for builds the platform runs from a connected repository. They do nothing for a folder publish. See [Publish from Git](/git).

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `build.rootDirectory` | string | none | Directory the build runs in |
| `build.installDirectory` | string | none | Directory the install runs in, when it differs |
| `build.installCommand` | string | none | Overrides the detected install command |
| `build.buildCommand` | string | none | Overrides the detected build command |
| `build.outputDirectory` | string | none | Where the build wrote its output |
| `build.ignoredBuildCommand` | string | none | A command whose exit code decides whether to skip the build |
| `build.frameworkPreset` | string | none | Pins the framework instead of detecting it |
| `build.platformPreset` | string | none | Pins the source platform preset |
| `build.allowUnsupportedPlatformFeatures` | boolean | none | Proceeds past unsupported migration features |
| `build.timeoutSeconds` | integer, 60 to 7200 | none | Build timeout |

Every field is nullable, and `build` is a closed object.

## Placement

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `placement.burstable` | boolean | none | Whether the site may burst its PHP workers |

Data location is chosen once, when the Space is created, and never changes.

## Runtime

One runtime per version, discriminated on `kind`. Omit the block for a static site.

### `kind: "zero"`

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `runtime.server` | string, required | none | Server entry, relative to the published directory |
| `runtime.client` | string, required | none | Client entry, relative to the published directory |

Both are required. Zero is never inferred. See [Dynamic sites with Zero](/zero-runtime).

### `kind: "functions"`

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `runtime.entry` | string | detected | Worker entry. Naming a file that does not exist fails the publish |
| `runtime.compatibilityDate` | `YYYY-MM-DD` | `2026-07-01` | Runtime semantics this worker was written against |

See [Functions](/functions).

## Crons

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `crons` | array, up to 8 entries | none | Scheduled requests |
| `crons[].path` | string, up to 512 chars | none | Path to GET. Starts with `/`, no query, no wildcards, no `:placeholders` |
| `crons[].schedule` | string | none | A named schedule, a shorthand, or a five-field crontab |

The project config is the only writer. See [Crons](/crons) for the schedule grammar.

## Access

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `access` | `"public"` or `{ public: string[] }` | none | Live paths that stay public whatever the Space's access setting is |

`"public"` is shorthand for `{ "public": ["/**"] }`. Prefix a pattern with `!` to exclude it, and use `*` and `**` as whole-segment wildcards. Patterns must be unique, and a non-empty list needs at least one inclusion. The declaration is inactive until the Space is claimed. See [Access](/access).

## Routing

`redirects`, `rewrites`, and `headers` are real config keys, owned by the routing compiler and merged behind the `_redirects` and `_headers` files. Their grammar, precedence, and every rule field live on one page.

See [Redirects, rewrites, and headers](/routing).

## Traffic rules

| Key | Type | Default | What it does |
| --- | --- | --- | --- |
| `firewall` | array, up to 50 rules | none | Requests to block or challenge before they reach the Space |
| `cache.bypass` | array, up to 50 rules | none | Requests that skip the cache |

A publish puts these rules at the edge. The Space settings can declare the same two keys, and their rules answer first. See [Traffic rules](/traffic-rules) for the rule fields.

## Accepted but not yet enforced

| Key | Type | What it does |
| --- | --- | --- |
| `markdownNegotiation` | boolean | Accepted by the schema. Runtime enforcement ships separately, so setting it changes nothing today |

## Parser caps

| Cap | Value |
| --- | --- |
| File size | 256 KiB |
| `templates` entries | 100 |
| `crons` entries | 8 |
| `crons[].path` | 512 characters |
| `name` | 255 characters |
| `meta.title` | 300 characters |
| `meta.description` | 1000 characters |
| `meta.image`, `meta.favicon` | 2000 characters |
| `superpowers.javascriptTags` entries | 16, each `code` up to 8 KiB |

A plan may lower these caps. None of them can be raised.

## The strict v1 shape

There is a second, stricter contract for the same files, selected by a top-level `"version": 1`. Its schema is published separately at `https://spacefast.com/schemas/sf.v1.json`, and `sf routing inspect` compiles against it.

In that shape the serving keys move into a `serve` block.

```jsonc sf.jsonc
{
  "$schema": "https://spacefast.com/schemas/sf.v1.json",
  "version": 1,
  "serve": {
    "index": "index.html",
    "spaFallback": "index.html",
    "cleanUrls": true,
    "directoryListing": false
  }
}
```

Under `version: 1` the flat spellings are rejected. Four of them get `config_unknown_key` with the replacement named in the message.

| Flat key | v1 spelling |
| --- | --- |
| `index` | `serve.index` |
| `fallback` | `serve.spaFallback` |
| `cleanUrls` | `serve.cleanUrls` |
| `meta` | `metadata` |

The v1 root accepts `$schema`, `version`, `build`, `serve`, `redirects`, `rewrites`, `headers`, `firewall`, `cache`, `metadata`, `substitute`, `access`, and `crons`. Anything else is an error. `listing`, `superpowers`, `templates`, `theme`, `placement`, and `markdownNegotiation` report `config_key_removed`; `space` reports `config_identity_moved`.

The flat shape above is what the finalizer reads and what the CLI writes. Use `version: 1` only if you want the stricter contract.
