`sf zero` builds and runs [Zero](/zero) apps: a `zero.config.ts` compiled to WordPress. The rest of this page covers WP-CLI, runtime status, site pages, design tokens, and analytics.

Every command here takes the global flags (`--api-url`, `--profile`, `--token`, `-y`/`--yes`, `--json`). `sf wp`, `sf runtime status`, and `sf analytics` also take the space selection flags (`--space`, `-o`/`--team`, `--claim-token`). See [the CLI overview](/cli).

To publish a Zero app, run `sf publish` from its root. See [Dynamic sites with Zero](/zero).

## sf zero init

Start a Zero app: a starter `zero.config.ts` with one collection, one table, and one action, named after the directory.

```text
sf zero init [name] [-f]
```

| Argument or flag | What it does |
| --- | --- |
| `[name]` | Directory to create. Omit to initialize the current directory |
| `-f, --force` | Overwrite an existing `zero.config.ts` |

It also adds `.zero/` and `node_modules/` to `.gitignore`. `sf init --runtime zero` writes the same starter.

```bash
sf zero init my-app
sf zero init
```

## sf zero check

Compile `zero.config.ts` and report diagnostics without writing anything.

```text
sf zero check [project] [--json]
```

Each diagnostic names a `file:line:col` and a fix. `--json` prints the diagnostics envelope instead of text. `sf zero check` uses the compiler bundled with the CLI, so it needs no native download.

```bash
sf zero check
sf zero check ./app --json
```

## sf zero dev

Run the app on a local WordPress and rebuild when its source changes.

```text
sf zero dev [project] [--port <n>] [--no-watch] [--allow-destructive]
sf zero dev stop [project]
sf zero dev status [project]
sf zero dev wp [project] -- <WP-CLI args>
```

`sf zero dev` boots WordPress through WordPress Studio, with no Docker. It needs Node 22 or newer, and the first start downloads WordPress and the plugins the app needs. It watches TypeScript, config, and `public/` files. Ctrl-C stops WordPress and keeps the local database for the next start.

| Argument or flag | What it does |
| --- | --- |
| `--port=<n>` | Port for a new local site. An existing site keeps its port |
| `--no-watch` | Start the site and return, without watching |
| `--allow-destructive` | Apply a schema change that drops or retypes data, once. Saves after that are protected again |
| `stop` | Stop the local site |
| `status` | Print whether the local site is running, and its URL |
| `wp -- <args>` | Run WP-CLI against the local site |

The login it prints is for local development only.

```bash
sf zero dev
sf zero dev --no-watch
sf zero dev wp -- user application-password create admin local --porcelain
sf zero dev stop
```

## sf zero build

Compile `zero.config.ts` into WordPress plugins.

```text
sf zero build [project] [--out <dir>]
```

It writes the plugins to `.zero/wp-content/`, new migrations to `zero/migrations/`, the typed client to `zero/client/`, and editor types to `zero.gen.ts`. Commit everything except `.zero/`.

```bash
sf zero build
sf zero build ./app --out ./dist
```

`sf zero dev` and `sf zero build` run the native compiler from the CLI's optional platform package. If it's missing, reinstall the CLI with optional dependencies enabled. Set `SPACEFAST_ZERO_BIN` to a `zero` binary to use your own build instead.

## sf zero import

Translate a Payload, EmDash, or Sanity schema into a new `zero.config.ts`, check that it compiles, and print what mapped and what did not. Fully local, no space flags.

```text
sf zero import <source> <input> [--out <file>]
```

| Argument or flag | What it does |
| --- | --- |
| `<source>` | `payload`, `emdash`, or `sanity`. `payloadcms` is accepted for `payload` |
| `<input>` | The schema file, or the project directory to find it in (`payload.config.ts`, `.emdash/seed.json`, `sanity.config.ts`) |
| `--out=<file>` | Config file to write. Defaults to `zero.config.ts`, and it must not exist yet |

It never runs code from the other CMS and never overwrites a file. Anything Zero cannot hold refuses the whole import, and nothing is written. Every write rule in the result starts as denied, so set `access` before you publish.

```bash
sf zero import payload ../my-payload-app
sf zero import emdash ../site --out app/zero.config.ts
```

### Output

One line per schema entry: its outcome, its JSON pointer, and the reason. With `--json`, `data` carries `source`, `from`, `out`, and `report.entries[]`.

## sf wp

Run WP-CLI against a Space's WordPress, or against a local one with `--local`.

Everything after the flags is passed to `wp` unchanged, so `sf wp plugin list --format=csv` runs exactly that. With `--local`, WP-CLI's own output and exit code pass through untouched. Against a Space, the command runs remotely and reports whether it succeeded and how long it took. The platform returns no stdout, including for read commands such as `sf wp option get`. `--json` wraps only Spacefast's own errors, never `wp`'s output. See [WordPress on every Space](/wordpress). Use `--` to pass a flag `sf` would otherwise claim.

```text
sf wp [--space <value>] [--local] [--path <dir>] [--mode full|limited] -- <wp args...>
```

### Flags

| Flag | Default | What it does |
| --- | --- | --- |
| `--local` | `false` | Run against a local WordPress instead of the Space's |
| `--path=<dir>` | none | Path to the local WordPress install. Implies `--local` |
| `--mode=<full\|limited>` | `full` | Remote only. `limited` skips the site's own themes and plugins, so a core command still answers on a broken site |

```bash
sf wp option get blogname
sf wp --space docs plugin list --format=csv
sf wp --local --path ./wordpress core version
sf wp -- --version
```

### Errors

| Code | Exit | When |
| --- | --- | --- |
| `wp_cli_php_missing` | 1 | `--local` and `php` could not be run. WP-CLI is a PHAR, so it needs PHP 7.2 or newer on your `PATH` |

## sf runtime status

Show what a Space is serving: its live version, the URL it answers on, and what the live version deployed when it ships code.

A worker lists entry, bundle digest, routes, endpoints, and capabilities. All of it comes from version metadata, so it answers while the runtime is asleep or moving.

```text
sf runtime status [--space <value>]
```

No arguments, no command-specific flags.

```bash
sf runtime status
sf runtime status --space docs
```

### Output

```text
State: active
Live version: ver_0123456789abcdef
Pending version: none
Live URL: https://docs.view.fast
```

Then one table per runtime section. A static Space has no app and prints nothing further.

With `--json`, `data` carries `liveVersionId`, `pendingVersionId`, `liveUrl`, `runtimeState`, `liveVersionStatus`, `pendingVersionStatus`, `app`, and `operation`.

## sf pages pull

Copy Spacefast's readable default page HTML into your project. Fully local. No API call, no space flags.

```text
sf pages pull [target]
```

### Arguments

| Argument | What it is |
| --- | --- |
| `[target]` | `all`, `layout`, or a site page id. Defaults to `all` |

The site page ids are `404`, `denied`, `access`, `index`, and `preview`. It writes `_layout.html` at the project root and `_pages/<id>.html` for each id. An existing file makes the write fail. There is no force flag, so move or delete the file first.

```bash
sf pages pull
sf pages pull 404
```

`_layout.html` gives your site chrome on every plan. `_pages/*.html` full-page takeovers are a paid-plan entitlement <Badge variant="accent">Plus and up</Badge>. See [limits](/limits).

## sf pages validate

Run the same structural page checks publish runs. Fully local.

```text
sf pages validate [-d <dir>]
```

### Flags

| Flag | Default | What it does |
| --- | --- | --- |
| `-d, --dir=<dir>` | `.` | Project directory |

Discovery skips `.git`, `.spacefast`, and `node_modules`, and collects only `_pages/**` and `_layout.html`. The theme is read from `theme.json`, then overridden by `sf.jsonc`'s `theme` key.

```bash
sf pages validate
sf pages validate -d ./dist
```

The command sets exit code 2 when any diagnostic has severity `error`. Warnings do not change the exit code.

## sf design generate

Read `DESIGN.md`'s ` ```theme.json ` and ` ```layout.html ` fenced blocks and write `theme.json` plus `_layout.html`. Fully local, no API call.

`theme.json` can seed Pages tokens. `_layout.html` provides site chrome. `DESIGN.md` itself is never read at finalize or serve time; this is an authoring-time codegen step.

```text
sf design generate [-f]
```

### Flags

| Flag | Default | What it does |
| --- | --- | --- |
| `-f, --force` | `false` | Overwrite existing generated files |

The command also accepts ` ```json:theme.json ` and ` ```html:layout.html ` fences. The first matching fence wins. Each block is validated with the same finalizer publish uses, and an invalid block produces a warning and is not written. Without `--force`, an existing target is skipped rather than overwritten. Files are written with mode `0644`.

```bash
sf design generate
sf design generate --force
```

### Output

With `--json`, `data` is `{ written, skippedExisting, warnings }`.

### Errors

| Code | Exit | When |
| --- | --- | --- |
| `validation_error` | 2 | No `DESIGN.md` in the current directory, or no usable fence in it |
| `design_doc_unreadable` | 1 | `DESIGN.md` exists but could not be read |
| `validation_error` | 2 | The output target is a symlink and `--force` was not passed |

## sf analytics

Print a Space's runtime analytics series.

The numbers are read live from the edge, not from a local store, and they cover every hostname mapped to the Space. `views` counts successful non-crawler requests, status under 400, assets included. That's why the per-day series prints instead of one total: daily uniques are the finest resolution available and are never summed across days.

```text
sf analytics [--space <value>] [--window 48h|7d|30d]
```

### Flags

| Flag | Default | What it does |
| --- | --- | --- |
| `--window=<48h\|7d\|30d>` | `7d` | Analytics window |

```bash
sf analytics --space docs
sf analytics --space docs --window 30d
```

### Output

```text
Window: 7d (2026-08-26T00:00:00Z → 2026-09-02T00:00:00Z)
Granularity: daily
Views: 18422 Bandwidth: 903841122
2026-08-26 visitors=612
/docs/quickstart views=2210
2026-08-26T00:00:00Z requests=3011 views=2874 bandwidth=140228311
```

With `--json`, `data` carries `spaceId`, `window`, `since`, `until`, `granularity` (`hourly` for `48h`, `daily` otherwise), `views`, `bandwidthBytes`, `visitorsByDay[]`, `topPaths[]` and `topHosts[]` (each capped at 10), and `series[]`.
