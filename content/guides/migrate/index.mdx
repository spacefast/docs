For a static site, the basic migration is two commands: publish the static
output your current host serves, then attach the domain. When the source host
already uses root `_redirects` and `_headers` files, keep them. Use the
[provider-specific guide](#choose-a-guide) to convert platform features before
cutover.

```bash
sf publish ./dist
```

```bash
sf domains add www.example.com --wait
```

## Check capacity and entitlements

Open the target team's **Usage & billing** page in the dashboard and
compare its storage, routing, domain, and publish limits with the needs of
the site you move. Gated routing features, such as external `200` proxy
rules, depend on the team's routing entitlements. Check the entitlements
in the dashboard before you rely on them.

## What carries over

Spacefast hosts static output. `_redirects` and `_headers` files, SPA
fallbacks, custom 404 pages, and external proxies (plan-gated) carry over,
and HTTPS certificates are automatic. If the source site needs request-time
code, move that work to build time, keep it in an external service, or add
[Functions](/functions).

To build on every push, with branch previews and status checks,
[connect a Git repository](/publish/git).

## Migration safety

- A publish with changed content creates an immutable version. Roll back with
  `sf rollback` or from the dashboard.
- Anonymous publishing works without an account. To keep the space, claim
  it within 6 hours.
- You can download any space version's files with `sf spaces download`.

## Cutover checklist

<Steps>
  <Step title="Build">Build the current static artifact.</Step>
  <Step title="Test publish">Publish to a test Spacefast space.</Step>
  <Step title="Verify">
    Check routing, headers, redirects, and image paths.
  </Step>
  <Step title="Move the domain">
    Add the production domain and wait for the DNS and certificate checks.
  </Step>
  <Step title="Hold the old host">
    Keep the previous host available until the new domain is healthy.
  </Step>
</Steps>
