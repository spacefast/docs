Visitor access comes from additive grants. Removing a public grant closes that route to the public only if no other public grant matches; links, people, and team access can remain.

## Access is a list, not a switch

Access is a set of additive **grants**, each one naming an audience, a set of capabilities, the paths it covers, and which published target it applies to. A matching grant admits a visitor. Revoking one grant does not revoke other matching grants or remove the owning team's permissions.

That model is why a Space can be public at `/docs/**` and closed everywhere else, and why revoking a share link takes effect on the next request rather than at the next publish.

The dashboard puts the three common shapes behind one control, and the CLI and API let you write any grant you want.

| Audience | Who it admits |
| --- | --- |
| `public` | Anyone on the web |
| `team` | Every member of the owning team |
| `person` | One invited person, by email |
| `link` | Whoever holds a share link |
| `password` | Whoever knows a password |
| `machine` | Whatever holds a bearer token |
| `external` | One subject proven by a team SSO or signer connection. See [SSO and external identity](/sso) |

## Roles

A role is a named bundle of capabilities. Every grant carries one.

| Role | Can |
| --- | --- |
| `viewer` | View pages |
| `commenter` | View, read comments, write comments |
| `editor` | The above, plus publish |
| `manager` | The above, plus manage access |

Share links and passwords are forwardable secrets, so they cap at `viewer` or `commenter`. Neither can be given `manage`. People, machine credentials, and external identities can hold any role.

`commenter` on the live site needs the Space's comments set to **Everywhere**. On a Space that keeps comments to previews, the write fails with `comments_target_unavailable`; grant `commenter` on a version instead.

## In the dashboard

Open the Space and go to **Access**. The page is titled **Manage access**.

The **General access** control has two positions, **Private** and **Public**. When it is set to Public, **What public visitors can do** sets the role: `viewer` or `commenter`. A Space whose team has turned on [Private spaces only](#defaults-for-new-spaces) cannot be switched to Public, with the reason "Your team only allows private spaces."

Next to it sits the **Password** card, then **Share link**, then **People** with its **Access requests**. **Advanced** is collapsed and holds **Path rules**, **Machine credentials**, and **SSO and identity**; it opens on its own when some paths have their own rules, with the note "Some paths are open to anyone on the web; the rest needs access. Path rules under Advanced list them." Path rules lists public and team grants path by path and can revoke them; creating one is a CLI or API job.

## Make a Space public

```bash
sf share grant --to public --role viewer --path '/**' --target live --space my-site
```

Scope it instead of opening everything:

```bash
sf share grant --to public --role viewer --path '/docs/**' --exclude '/docs/internal/**' --space my-site
```

`--to team` does the same for the owning team. Patterns use `*` for one segment and `**` for zero or more. A grant takes up to 100 patterns, includes and excludes combined.

A public grant cannot carry publish or manage capabilities.

Grants default to `live`. Opening the live site does not open branch previews or version URLs. To make immutable version URLs public too, add a grant for `all-versions`:

```bash
sf share grant --to public --role viewer --path '/**' --target all-versions --space my-site
```

Use `version:<id>` to open only one version. Branch previews need a `branch:<name>` grant; `all-versions` does not cover them or the live site. A public grant cannot target a branch, so share a branch preview with a link, a password, or a person instead. A team grant admits the owning team; it cannot name another team you belong to.

## Share links

A new team-owned Space does not create a share link in the current CLI or dashboard. The owning team signs in at the live URL. Create a link when you want to share outside the team.

Team requests to `POST /v1/spaces` that do not send `capabilities: ["optional_access"]`, such as older CLI versions and dashboard tabs, still receive a compatibility Open link. Team Spaces created by current publish clients get no automatic link. Team requests that send the capability get no link, and their successful receipt can omit `access`. Anonymous Spaces keep their expiring Open link.

A share link is a durable URL that opens exactly the paths you scoped it to, with no account needed. The secret rides in the query string, so the link is the page:

```text
https://my-site.view.fast/docs?__=sfl_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

One request returns that document. There is no redirect and no interstitial, so `curl`, an agent, and a browser all get the same page.

### Create one

```bash
sf share link create \
  --space my-site \
  --name "Client review" \
  --landing /docs \
  --path '/docs/**' \
  --path '/assets/**' \
  --exclude '/docs/internal/**' \
  --role commenter \
  --expires 7d
```

| Flag | Default | What it does |
| --- | --- | --- |
| `--name` | required | The name shown in the links list |
| `--landing` | `/` | The clean route the link opens at. It has to be inside the link's paths |
| `--path` | `/**` | An included pattern. Repeat for disjoint subtrees |
| `--exclude` | none | An excluded pattern, local to this link |
| `--role` | `viewer` | `viewer` or `commenter` |
| `--target` | `live` | `live`, `all-versions`, `version:<id>`, or `branch:<name>` |
| `--not-before` | none | Do not admit anyone before this timestamp |
| `--expires` | never | A duration such as `30m`, `24h`, `7d` |
| `--max-uses` | unlimited | Successful opens before the link stops working, 1 to 1,000,000 |
| `--require-verified-email` | off | Admit only visitors whose session has a verified email |
| `--country` / `--exclude-country` | none | Allowed or blocked ISO country codes |
| `--exclude-user-agent` | none | Block user agents containing this text |

In the dashboard, the **Share link** card's **Create share link** button opens a sheet with the same fields, labelled **Name**, **What link holders can do**, **What the link opens**, **Opens at**, **Paths**, **Starts**, **Expires**, **Maximum opens**, and a **Require a verified email** toggle.

### List, copy, revoke

```bash
sf share link ls --space my-site
sf share link copy lnk_xxxxxxxx --space my-site --show-secret
sf share link revoke lnk_xxxxxxxx --space my-site
```

List reads never carry the secret. The URL is returned only to callers who may manage the Space's access, and `--show-secret` is what prints it in a non-interactive shell.

Revoking drops the grant in the same write, so every outstanding copy of the URL stops working on the next request.

`sf share link edit` changes a link's scope, role, target and constraints without rotating its URL, so a link you already sent can be narrowed rather than replaced.

A Space that has not been claimed yet may keep up to 50 active links, and further creates return `anonymous_share_link_limit`.

## Passwords

A password is a separate audience with its own scope, not a lock on the whole Space. Several named passwords can coexist, each covering different paths.

```bash
sf share password create \
  --space my-site \
  --name "Beta testers" \
  --path '/**' \
  --role viewer \
  --password-from-stdin
```

Pass the value on stdin, or through `SPACEFAST_SHARE_PASSWORD`. It never goes into `sf.jsonc`. A password needs at least 15 characters; the dashboard's **Generate password** button makes one. The verifier is Argon2id.

```bash
sf share password ls --space my-site
sf share password rotate pwd_xxxxxxxx --space my-site --password-from-stdin
sf share password revoke pwd_xxxxxxxx --space my-site
```

Rotating keeps the grant and its scope, and immediately signs out sessions that used the old password. Revoking removes the grant, so those sessions lose access too.

The dashboard's **Password** card carries **Set password**, **Change password** and **Remove password**, with **Expires**, **Paths** and **What password holders can do** under **Password options**. It manages one password; the card's own footnote points at the CLI and API for more.

## Inviting people

```bash
sf share people invite person@example.com --space my-site --role commenter --scope /docs
sf share people ls --space my-site
sf share people remove person@example.com --space my-site
```

`--scope` defaults to `/` and is repeatable, so one invitation can grant the same role on several subtrees. `--target` picks what they get, defaulting to `live`.

In the dashboard, the **People** card takes an email, a **What they can do** role, and a **What they get access to** scope. Pending rows show **Invitation pending** with **Resend** and **Remove** actions.

A person can hold up to 32 scoped grants on one Space, so one collaborator can have different roles on different subtrees. An invitation expires after 7 days; **Resend** issues a fresh one.

## Machine credentials

For a script or a job, issue a bearer token rather than sharing a link:

```bash
sf share token create --space my-site --name "Nightly export" --path '/exports/**'
sf share token ls --space my-site
sf share token rotate mch_xxxxxxxx --space my-site
sf share token revoke mch_xxxxxxxx --space my-site
```

The token is shown once, right after creation. The dashboard says it plainly: "Copy it now. It won't be shown again." Rotating keeps the grant and its scope and invalidates the old token immediately.

A machine credential can hold any role. `viewer` reads pages; `editor` can also publish to that Space through the API; `manager` can also manage its access. The dashboard form sets name, paths, role, and expiry on the live target; use the CLI for other targets or exclusions.

Send the token differently depending on where the request goes:

| Request to | Header |
| --- | --- |
| The Space itself, such as `https://my-site.space.fast/exports/latest.csv` | `X-SF-Authorization: Bearer sfm_…` |
| The Spacefast API, such as a publish | `Authorization: Bearer sfm_…` |

On the Space, the ordinary `Authorization` header belongs to your own application and passes through untouched, so it never admits a visitor.

## Access requests

A visitor who lands on a Space they cannot open can ask for access. The form takes an email and an optional message of up to 280 characters, and the visitor confirms the request through an emailed link within 30 minutes. Team owners and admins get an email with a review link. Requests show up in the **Access requests** card and in the CLI:

```bash
sf share request ls --space my-site
sf share request approve arq_xxxxxxxx --space my-site
sf share request deny arq_xxxxxxxx --space my-site
```

Approving invites the requester to the path they asked about, as a `viewer` unless you pass `--role`. The dashboard's **Approve as Can view** offers the exact path or its subtree. The requester gets an email either way. A Space holds at most 25 pending requests, and a request expires after 14 days.

A person who already accepted an invitation but lost their session gets back in the same way: a confirmed request that their existing grants already cover is approved on its own.

## What a visitor sees

**On a public Space**, the page loads. No access code runs at all.

**With a share link**, the link is the page. The token is redeemed before anything is read from disk, so the first request returns the document. The response is never stored in any cache. It also carries `Referrer-Policy: no-referrer`, so the secret does not leak through the referrer header on outbound clicks.

**On a protected Space with no proof**, the request answers **403** with the Space's access page and `Cache-Control: private, no-store`. On a claimed Space, the page offers **Continue with Spacefast** and a request-access form. It adds a password box when the Space has a password, and a **Continue with &lt;provider&gt;** button for each [SSO connection](/sso) the Space has a grant for.

**Signing in** sends the visitor to Spacefast, then back. The path they originally asked for is carried through the round trip, so they land on the page they wanted rather than the homepage.

**Submitting a password** posts it from the same origin and checks it against the platform, not anything on the box. On success, it sets the visitor's session cookie and sends a **303** back to where they were. Passwords are capped at 1024 bytes. Failures come back as rate limited, invalid password, or exchange unavailable.

**A link or password created with `--require-verified-email`** adds one step: the visitor enters an email and clicks the confirmation link it receives within 15 minutes. The proof is good for an hour on that credential, after which the visitor confirms again. Public grants and machine credentials cannot require it.

A visitor session is idle-expiring after 7 days and absolutely expiring after 30 days.

Two behaviors are worth knowing because they look like bugs and are not. A rewrite cannot widen access: both the URL the visitor asked for and the path it rewrote to have to be admitted. And a directory listing on a protected Space silently omits the rows that visitor cannot reach, rather than showing them and challenging.

## Revoking everything at once

```bash
sf access logout-all --space my-site
```

This ends every active visitor session on the Space, whatever admitted them: share link, password, private open, or signed-in account. It takes effect immediately, without a republish. Grants themselves are untouched, so anyone still holding a valid link or password can open the Space again on their next visit. Revoke the grant when you want the credential itself dead.

## Defaults for new Spaces

A team decides what its new Spaces start as. In the dashboard, open team settings, go to **Access**, and use the **Space access** card's **New spaces are** row.

| Preset | New Spaces start with |
| --- | --- |
| `private` | Access for the owning team |
| `public` | Access for the owning team, plus view access for anyone on the web |

The default is `private`. The API accepts the legacy value `team` and normalizes it to `private`. Changing the default applies only to Spaces created after the change. Neither preset creates a share link on its own.

The same card holds two team-wide switches:

- **Private spaces only**. While it is on, no Space in the team can be public. Turning it on revokes every public grant on the team's Spaces, and from then on a public grant, a `public` default, and `access` in `sf.jsonc` are refused or ignored with `team_private_spaces_only`. Invites, share links, and passwords keep working. Spaces this switch made private stay private after you turn it off.
- **Hide from search engines**. Every Space in the team serves `noindex` on its live hostnames, whatever the Space's own setting says. It stays on while Private spaces only is on.

Only team owners and admins can change these, and only from the dashboard; `sf teams defaults` shows them but cannot change them.
