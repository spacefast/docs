:::note[Not sure where to start?]
Open your Space in the dashboard first. Its **Overview** page shows the last publish and its status. Come back here once you have an error code or a symptom from the list below.
:::

## Publishing

### The publish says nothing changed

The files you published match the live version exactly, so no new version was created. The receipt has a null version ID and one info diagnostic, `noop_publish`. The publish still succeeded.

If you expected a change, check that you published the built output and not a stale directory. A file declared without a `sha256` can't be compared, so a manifest with any missing hash always creates a new version. See [Publishing](/publish).

### The publish was rejected

These errors fail the whole publish instead of skipping the file, because skipping it would change what your Space serves.

| Code | What happened | Fix |
| --- | --- | --- |
| `version_file_too_large` | One file is over the per-plan ceiling | Host the asset elsewhere, or move up a plan |
| `manifest_too_many_files` | More files than your plan allows | Publish the build output directory, not the source tree |
| `invalid_file_path` | A path Spacefast cannot canonicalize | Remove backslashes, doubled slashes, and trailing dots or spaces |
| `static_control_file_not_supported` | An `.htaccess` or `.user.ini` shipped | Delete it and use `_redirects` and `_headers` instead |

Every limit and its number is on [Limits](/limits). Every code, with whether retrying helps, is on [Error codes](/api/errors).

### The publish failed while provisioning

`publish_setup_failed` means provisioning for this publish did not complete. It isn't a limit, and nothing is wrong with your files. Retry the publish. If it persists, contact support with the `requestId` from the error, or [send feedback](/feedback) with the code and request ID attached.

`publish_session_expired` is different. Declared uploads are kept for 24 hours. A publish resumed after that has to start over.

### The build failed

Read the log before changing anything.

```bash
sf builds list --space my-site
sf builds logs bld_xxxxxxxx --follow
```

Each code points at a different cause. `build_failed` means your command exited non-zero. `build_timeout` means the build hit the time limit. `build_oom` means the build was killed, most likely because it ran out of memory. `build_output_dir_missing` means the build finished but the output directory you named was never produced. `build_no_index_html` means it produced output with no `index.html` at the root. Detection defaults, override flags, and the log limits are on [Frameworks and builds](/frameworks).

## Serving

### The site still shows the old version

Public HTML defaults to `public, s-maxage=600, max-age=0, must-revalidate`, and other unhashed files to `s-maxage=86400`. Your browser revalidates those on every load, but a shared copy can be up to ten minutes stale for a page and up to a day for other files. Unhashed files under build output directories are the exception: browsers can keep them for a year. Protected responses, conditional routing, and header overrides follow the exceptions on [Caching](/caching).

Activating a new version requests a purge of the Space's serving hostnames; immutable version hostnames are not purged. If the purge isn't confirmed, you get a `runtime_purge_failed` diagnostic and the runtime retries. Even then, a shared copy of a page expires after ten minutes. Check which version answered you:

```bash
curl -sI https://my-site.space.fast/ | grep -i x-spacefast-version
```

Full policy on [Caching](/caching).

### A route 404s that works locally

Spacefast resolves URLs with three rules that your local dev server may not follow.

Clean URLs are on by default, so `about.html` answers `/about` and `/about/` redirects to `/about` with a 308. A directory serves its `index.html`. A single-page app gets a fallback shell inferred from a root `200.html`, `_shell.html`, or an `index.html` next to build output, or set `fallback` yourself. The fallback is skipped for around 90 asset extensions, so a missing `.js` returns 404 instead of your HTML shell.

If two files would answer the same URL under these rules, the publish fails with `publish_path_collision`. See [Redirects, rewrites, and headers](/routing).

## Domains

### The domain is stuck on `pending`

`pending` means assigned and waiting for the records to appear in public DNS. Run the diagnostics first:

```bash
sf domains diagnostics example.com --space my-site
```

`dns_records_missing` means the records have not been observed yet. The usual cause is a leftover `A` record from your previous host sitting beside the correct one. Every observed `A` record has to point at Spacefast, so delete the old ones, and any `AAAA` left from your previous host. An apex gets two `A` records and a `www` CNAME; a TXT record appears only when the hostname is in use elsewhere. See [Custom domains](/domains).

### The domain went `failed` after working

`failed` means there is no current proof that you control the DNS. Either the records were never observed, or the domain verified once and later stopped verifying. Check whether someone edited the zone.

A failed verification doesn't take a live Space down right away. Routes and certificates stay in place while the domain verifies again. Run `sf domains diagnostics` to see which records are observed now, and restore the TXT record if it is the one that went missing.

### The certificate is `broken`

Issuance failed because something in the zone is blocking it. The usual cause is a CAA record that doesn't allow the issuing authority, which shows up as `ssl_renewal_blocked` in the diagnostics.

Fix the CAA record, then retry. Verification checks and certificate retries are each limited to 6 per hour per domain and 120 per hour per team. Past that, the API answers `rate_limited`, so retrying in a loop won't help.

### `www` redirects when you wanted it to serve

Adding an apex also adds its `www` hostname, and adding `www` also adds the apex. One of the pair serves the Space and the other redirects to it with a `308`. Spacefast creates that redirect for you, and both hostnames can't serve at once.

Set the one you want as **primary**, which releases the previous holder. A domain carrying a redirect cannot be primary, and promoting it without clearing the redirect fails with `domain_primary_redirect_conflict`. See [Custom domains](/domains).

## Credentials and automation

### `sf login` has no browser to open

In a container or over SSH, the CLI doesn't try to open a browser. It prints the code and the link, then waits. Open the link on any device and approve the request. The CLI continues once you approve.

For an unattended job, skip device login. Mint an API key and pass it as `SPACEFAST_TOKEN` or `--token`. See [Publish from CI](/ci) and [API keys and tokens](/api-keys).

### `confirmation_required` in CI

A truthy `CI` puts the CLI in agent mode, which adds `--json` and turns off prompts. It doesn't imply `--yes`, so a destructive command that can't ask for confirmation fails with `confirmation_required` and exit code 2.

Add `--yes` to the command that needs it. `SPACEFAST_YES=1` also works, but it confirms every destructive command in the job.

### The credential stopped working after a week

A credential from `sf login` lasts 30 days and expires after 7 days without use, whichever comes first. The API answers `401` with `credential_expired`. Run `sf login` again.

`credential_revoked` means someone revoked it, in the dashboard or with `sf api-keys revoke`. `credential_retired` means the token uses an old format. Retrying won't fix either one; get a new credential. See [Authentication](/authentication).

### An agent in a cloud sandbox cannot reach Spacefast

Claude Code on the web and mobile, Codex cloud, and similar hosted sandboxes block unknown hosts by default, including Spacefast. The CLI fails with `network_error` or `upload_transport_error`, and the agent can't read these docs either. There are three fixes, best first:

1. **Add the Spacefast connector to Claude.** [Open the connector form](https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Spacefast&connectorUrl=https%3A%2F%2Fmcp.spacefast.com) and choose **Connect**. Approve it, then enable it for the session. Connector traffic goes through Anthropic rather than the sandbox, so publishing works with no network changes, including from the mobile app.
2. **Push to a connected GitHub repository.** Sandboxes can push to GitHub, and Spacefast builds the push itself. Connect the repository once from the Space's **Builds** page; see [Connect a GitHub repository](/git#connect-a-github-repository). Claude Code on the web pushes a working branch, which builds a preview; merge the pull request to go live.
3. **Allow the hosts.** Add `spacefast.com`, `*.spacefast.com`, `*.space.fast`, and `*.view.fast` to the environment's allowlist. In Claude Code that is **Network access → Custom → Allowed domains**. Keep **Also include default list of common package managers** checked, or npm — and the CLI with it — is blocked too. In Codex cloud, turn on **Agent internet access** and add the domains. Leave HTTP methods unrestricted, since uploads use `PUT` and `POST`. Allowing only `api.spacefast.com` is not enough: uploads go to managed Space hostnames. New Spaces use `*.space.fast`, and existing Spaces can still use `*.view.fast`.

### An agent gets 403 on one tool

Each tool has its own scope requirements, so a grant can allow most tools and still refuse one. `publish` needs `publish:write`. `show_space_deployments` and `show_space_analytics` need `spaces:read`. `show_space_domains` needs `spaces:read` and `domains:read`.

The failure is `insufficient_scope`, and the `WWW-Authenticate` header names the scopes that were missing. Reconnect the client with those scopes. Some actions are reserved for a signed-in person at every level, and those answer `authorization_level_not_allowed` no matter what you grant. See [What agents are allowed to do](/agents/permissions).

### You are being rate limited

Every rate-limited response carries `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` in seconds. A `429` adds `Retry-After`, also in seconds. Wait that long. The code is `rate_limited`.

When an hourly limit rejected you, those headers describe the hourly window, not the per-minute one, so the wait can be long. Rate limiting fails open, so the headers are sometimes missing. Don't write client code that requires them. See [Rate limits](/api/rate-limits).
