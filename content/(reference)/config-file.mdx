`spacefast.config.ts` is the primary configuration file for Spacefast projects and what `sf init` creates. `sf.jsonc` and its JSON/JSONC aliases remain permanently supported and accept the same keys. The CLI evaluates TypeScript at build or publish time and freezes the resolved JSON into the version; the server never runs TypeScript on visitor requests.

## Example

Create `spacefast.config.ts` at your project root using `defineConfig` from `spacefast/config`:

```ts spacefast.config.ts
import { defineConfig } from "spacefast/config";

export default defineConfig({
  name: "My Space",
  cleanUrls: true,
  fallback: { path: "index.html", status: 200 },
  redirects: [{ source: "/old", destination: "/new", status: 301 }],
  headers: [{ source: "/assets/*", headers: [{ key: "X-Frame-Options", value: "DENY" }] }],
  crons: [{ path: "/api/digest", schedule: "daily" }],
  build: { buildCommand: "npm run build", outputDirectory: "dist" },
});
```

## File discovery and precedence

The CLI searches the project root in this order, and the first file found wins:

1. `spacefast.config.ts`
2. `sf.jsonc`
3. `spacefast.jsonc`
4. `spacefast.json`
5. `sf.json`
6. `.sf/sf.json`
7. `.sf/config.jsonc`
8. `.sf/config.json`

The CLI ignores other TypeScript or JavaScript filenames, including `spacefast.config.mts` and `spacefast.config.js`. All eight files stay private and never serve to visitors.

Keep one serving config file in a project:

- If several exist, the CLI uses the highest-priority file and warns about each ignored file.
- If the winning file fails to load or validate, the command stops with `config_invalid` (exit 2); it does not fall back to a lower-priority file.
- An explicit `--config` path (or `SPACEFAST_CONFIG`) on `sf git` commands selects that file for repository build settings; a missing path fails with `config_not_found` (exit 2).

### Coexistence with `spacepress.config.ts`

You can declare app definitions (collections, tables, actions, pages, routes, auth, plugins, admin, and locales) either inline under the `app` key in `spacefast.config.ts` or in a standalone `spacepress.config.ts` beside `spacefast.config.ts`.

- Putting serving settings in `spacefast.config.ts` and app definitions in `spacepress.config.ts` keeps both files working side by side.
- Define your app in either `spacepress.config.ts` or the inline `app` block of `spacefast.config.ts`, not both; [`sf publish`](/cli/reference#sf-publish-dir) and [`sf check`](/cli/reference#sf-check-dir) refuse a project that declares both at once.

### JSONC fallback (`sf.jsonc`)

`sf.jsonc` and the other JSON filenames accept JSON with comments and are capped at 256 KiB. Set `$schema` to `https://spacefast.com/schemas/sf.json`. Spacefast reads it as the format marker; for editor completion today, write `spacefast.config.ts`, whose `defineConfig` types cover every key:

```jsonc sf.jsonc
{
  "$schema": "https://spacefast.com/schemas/sf.json",
  "name": "My Space",
  "cleanUrls": true
}
```

## TypeScript configuration

`spacefast.config.ts` is an ES module whose default export is an object, a promise of an object, or a synchronous or async function returning an object.

```ts spacefast.config.ts
import { defineConfig } from "spacefast/config";
import { siteTitle } from "./config/meta";

export default defineConfig(async () => ({
  name: siteTitle,
  cleanUrls: true,
}));
```

`spacefast/config` exports three symbols:

| Export | Kind | What it does |
| --- | --- | --- |
| `defineConfig` | function | Returns its argument unchanged while type-checking the default export |
| `SpacefastConfig` | type | The config object shape |
| `SpacefastConfigInput` | type | `SpacefastConfig`, a promise of it, or a factory function returning either |

`defineConfig` is optional; you can type a plain export with `satisfies SpacefastConfig`. The installed CLI resolves `spacefast/config` when loading your file, including global and standalone installs. For editor type checking, add `spacefast` as a dev dependency:

```bash
npm install --save-dev spacefast
```

How evaluation works:

- The CLI bundles `spacefast.config.ts` and its relative imports, while leaving package imports and Node.js built-ins external so they resolve from your project directory.
- `sf build`, `sf publish`, and Git repository builds load the config before running `installCommand`, so avoid third-party package imports unless they are already installed.
- The resolved value must be a JSON-compatible object. The CLI omits properties set to `undefined` when writing JSON. Non-JSON values such as `Date` fail with `config_invalid`.
- Configuration is executable code. Only build repositories you trust, and never store secrets in config files.

### How TypeScript config ships and `.spacefast/config-source.ts`

When `sf publish` or `sf build` packs a version, the CLI evaluates `spacefast.config.ts` and writes the resolved JSON into the version as `sf.jsonc` without modifying your local files.

The CLI also stores your authored `spacefast.config.ts` inside the version at `.spacefast/config-source.ts` so each version records which TypeScript config produced it:

- `.spacefast/config-source.ts` is never served to visitors.
- Your team can inspect it with the version's uploaded files.
- `spacefast.config.ts` is also part of your source repository. If you enable public source sharing (`sf source availability`), anyone can read `spacefast.config.ts` on the main branch. Keep tokens and internal URLs out of the file and read them from Space variables instead. The first time you publish a Space whose source is public, `sf publish` prints a one-time warning.

Git repository builds evaluate a committed `spacefast.config.ts` inside the isolated build environment. Raw file uploads through the API and hosted MCP inline publishing cannot execute TypeScript config and reject an uploaded `spacefast.config.ts`. To publish prebuilt output without losing TypeScript config, run `sf build` and then `sf publish .spacefast/build-output.tgz --prebuilt`.

### Migrate from `sf.jsonc`

Migration is optional; `sf.jsonc` stays permanently supported. There is no `sf migrate config` command (`sf migrate` imports an external website from a public URL).

1. Create `spacefast.config.ts` beside your existing `sf.jsonc` (or rename the file).
2. Add `import { defineConfig } from "spacefast/config";` at the top and wrap your existing object in `export default defineConfig(...)`. Quoted keys, `//` comments, and trailing commas remain valid TypeScript. Remove `$schema`.
3. Keep all existing settings, including `runtime`, routing rules, `crons`, and `build`.
4. Run `sf build` (or `sf check`) from the project root to validate your configuration without publishing.
5. Delete the old `sf.jsonc` once validation passes. Keep `.spacefast/space.json` untouched so your Space link stays intact.

## Key details

### Identity and compatibility

- `name` sets the Space's display name. While `name` is declared in your config, the API refuses to rename the Space; edit the config and publish instead.
- `compatibilityDate` (`YYYY-MM-DD`) pins config behavior for the version. If omitted, Spacefast records the publish date on the version so later platform changes do not alter older versions.

### Serving

- `index` defaults to root `index.html` when present, otherwise a `200`-status `fallback` target (when no Worker runs), otherwise a single HTML file in the version or root, otherwise `false`.
- `fallback: { path: "index.html", status: 200 }` declares a single-page app shell and disables `listing` unless set explicitly. Naming a file not in the version fails the publish.
- `cleanUrls` defaults to `true`, so `about.html` serves at `/about` ahead of any fallback.

### Redirects, rewrites, headers, and traffic rules

- `redirects` entries accept `source`, `destination`, optional `status` (`301`, `302`, `303`, `307`, `308`; default `302`), optional `force`, and optional `query`.
- `rewrites` entries accept `source`, `destination` (local path or absolute `https://` URL to proxy), optional `cache: "shared"` (proxy destinations only), optional `force`, optional `query`, and optional `notFound: true` (local paths only).
- `headers` entries accept `source` and a non-empty `headers` array of `{ key, value }` or `{ key, remove: true }`.
- `firewall` holds up to 50 rules (`action: "block" | "challenge"`, optional `status` `400`–`499` for blocks, `match`, optional `any`, `name`, `description`).
- `cache.bypass` holds up to 50 rules (`match`, optional `any`, `name`, `description`) for requests that skip the edge cache.

Rules declared in Space settings (through the dashboard, CLI, or API) match ahead of rules declared in your config file. See [Redirects and rewrites](/redirects) and [Headers](/headers).

### Runtime, crons, and environment variables

One `runtime` block per version, discriminated on `kind`:

- `kind: "functions"`: optional `entry` (auto-detected from `.open-next/worker.js`, `handler.ts`/`js`/`mjs`, or `functions/` when omitted; naming a missing file fails publish) and optional `compatibilityDate` (`YYYY-MM-DD`). See [Functions](/functions).
- `kind: "zero"`: `server` (required) and `client` (defaults to the scaffold entry). See [Migrating from Zero 0.8](/zero-migration).

`crons` accepts up to 8 entries, each with `path` (literal `/...` path up to 512 chars, no wildcards, placeholders, or query string) and `schedule` (`hourly`, `daily`, `twicedaily`, `weekly`, `Nh`/`Nd`/`Nw`, or a numeric five-field crontab). Your plan determines how many declared crons run; see [Crons](/crons).

Environment variables and secrets do not live in `spacefast.config.ts` — set them with `sf env set` or in the dashboard, and list files under `templates` (up to 100) for build-time `{{ vars.NAME }}` substitution. Use `security.secrets.allowlist` (`entries`, `fingerprints`, `paths`, or `rules`, up to 128 each) only to suppress confirmed secret-scan false positives.

### Connectors and app

- `connectors` maps up to 32 camelCase role names to `{ connector, as?, tools, args?, cache? }`, where `as` is `"team"` (default), `"personal"`, or `"visitor"`, `tools` is `"*"` or up to 200 tool names, and `cache` defaults to `"30s"` (up to `"1440m"`, `"0"` disables reuse).
- `app` accepts `name`, `collections`, `tables`, `actions`, `pages`, `routes`, `auth`, `plugins`, `admin`, and `locales`. See [Collections](/collections) and [Actions](/actions).

### Access, public identity, theme, and snippets

- `access` accepts `"public"` (shorthand for `{ public: ["/**"] }`) or `{ public: string[] }` (up to 100 unique patterns; prefix exclusions with `!`; `*` and `**` match whole segments). The declaration stays inactive until you claim the Space, and Spacefast ignores it while the team has **Private spaces only** turned on. It compiles to one public `viewer` grant on `live` that `sf share revoke` cannot remove; edit the config and publish instead. See [Share and access](/share).
- `public` sets the Space's external identity (`title`, `description`, `icon`, `accent`, `ogImage`, `hideOnPrivateLinks`) shown on link previews and access gates, separate from the team-internal `name`.
- `theme` accepts `accent`, `background`, `logo`, `name`, `font`, and `hideSpacefastBranding` (closed object; colors accept hex, `rgb()`, `rgba()`, `hsl()`, `hsla()`, and CSS color names). A sibling `theme.json` acts only as an inference input (`settings.color.palette` and `settings.typography.fontFamilies`).
- `superpowers` configures `enabled`, `disable_all_injection`, `googleAnalytics`, `googleTagManager`, `javascriptTags` (up to 16 entries, each `code` up to 8 KiB), and `tags` (`inheritance`, `requireReview`).
- `inject` accepts static HTML snippet arrays under `head`, `bodyStart`, `bodyEnd`, and `noscript` (up to 16 snippets per slot, 8 KiB per snippet).
- `build` is a closed object accepting nullable `rootDirectory`, `installDirectory`, `installCommand`, `buildCommand`, `outputDirectory`, `ignoredBuildCommand`, `frameworkPreset`, `platformPreset`, plus boolean `allowUnsupportedPlatformFeatures` and integer `timeoutSeconds` (`60` to `7200`, default `900`).

## Optional `_redirects` and `_headers` files

`_redirects` and `_headers` at the root of your published directory are optional convenience and migration files. Both are private and never served as content (requesting one returns `404`).

When you combine them with `spacefast.config.ts` or `sf.jsonc`:

- Redirect and rewrite rules merge in this order: `_redirects` first, then config `redirects`, then config `rewrites`. First match wins. A config rule shadowed by an unconditional `_redirects` line reports a `redirect_shadowed_by_file` warning.
- Header rules merge with `_headers` winning over config `headers` when both set the same header name.

For new projects, declare `redirects`, `rewrites`, and `headers` in `spacefast.config.ts` so all Space configuration lives in one typed file. Validate changes offline with [`sf check`](/cli/reference#sf-check-dir) (invalid configs return [`config_invalid`](/errors/config_invalid)). See [Redirects and rewrites](/redirects) and [Headers](/headers).

## Limits

Parser caps enforced on every plan (plans may lower some runtime allowances, never raise these caps):

| Cap | Value |
| --- | --- |
| Resolved config size (`sf.jsonc` or evaluated `spacefast.config.ts`) | 256 KiB |
| Stored API config overlay size | 16 KiB |
| `templates` entries | 100 |
| `crons` entries | 8 |
| `crons[].path` length | 512 characters |
| `connectors` roles | 32 (up to 200 tools per role) |
| `firewall` rules | 50 |
| `cache.bypass` rules | 50 |
| `access.public` patterns | 100 |
| `name` length | 255 characters |
| `meta.title`, `public.title` length | 300 characters |
| `meta.description`, `public.description` length | 1,000 characters |
| `meta.image`, `meta.favicon`, `theme.logo`, `public.ogImage` length | 2,000 characters |
| `superpowers.javascriptTags` / `inject` snippets | 16 per list, up to 8 KiB each |

### Strict `version: 1` shape

Adding `"version": 1` selects a stricter contract described at `https://spacefast.com/schemas/sf.v1.json` (used by `sf routing inspect`). In `version: 1`, flat serving keys move under `serve` (`serve.index`, `serve.spaFallback`, `serve.cleanUrls`, `serve.directoryListing`) and `meta` becomes `metadata`. The flat shape documented above is what `sf init` writes and what the finalizer consumes by default.
