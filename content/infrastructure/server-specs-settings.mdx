Spacefast manages the servers behind your Space. You publish files and configure application behavior; the infra handles hardware, replication, and the shared edge network.

## Underlying infra

WP Cloud runs origin pools on AMD EPYC processors with NVMe storage and redundant 25 Gbit networking per server. Primary and secondary servers sit in different regions for [automated failover](/infrastructure/automated-failover). Hardware and software change as the platform upgrades pools.

Those are pool specifications, not dedicated resources reserved for each Space. Your product entitlements come from your [plan limits](/limits).

## PHP and compression

WP Cloud's default PHP memory limit is 512 MB per request. The platform supports larger per-site values, but Spacefast manages the settings for its sites. A WP Cloud capability does not create a matching Spacefast configuration field.

The infra supports Brotli and gzip compression. A client that accepts Brotli can receive it; gzip is available as a fallback. Compression headers belong to the platform, so do not set `Content-Encoding` in your published header rules.

For application access to WordPress, use the documented [WordPress commands and Abilities](/wordpress). The underlying PHP configuration is not a promise that arbitrary uploaded PHP files will execute.

## Configuration boundaries

| Change | Spacefast path |
| --- | --- |
| Redirects, rewrites, and response headers | Publish `_redirects`, `_headers`, or the supported [routing configuration](/routing). |
| Application environment variables | Use [Environment variables](/environment-variables). |
| Runtime configuration | Use the documented [Zero configuration](/zero). |
| Storage and resource entitlements | Check [Limits](/limits). |

Spacefast rejects authored `.htaccess` and `.user.ini` files. You cannot replace the managed server configuration or `php.ini` through a publish. Use the supported configuration for the behavior you need.
